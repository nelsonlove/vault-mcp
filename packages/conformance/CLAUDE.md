# Vault MCP Conformance (plugin id `vaultmcp-conformance`) — architecture & working notes for Claude Code

The conformance rail as its own Obsidian plugin: the rule packs run over the vault, the findings are compared with the accepted-debt baseline, and what is carried, cleared and new is reported. It publishes two MCP tools to the Vault MCP host through `vault-mcp-api`, adds the Drift pane, owns the vault-conventions setting, and carries the standalone CLI. Extracted from the host on 2026-10-14 (Nelson: "the conformance and scheme features still in core (i see em on the settings pages) need to be split out into satellites, either new ones or ones that already exist"), as suite-split-design.md §6 always planned. Package layout and commands are in `README.md`; the user-facing model is `docs/conformance.md` at the repo root.

## Locked decisions (don't relitigate without reason)

- **The published tool names changed.** `obsidian_conformance_debt` → `vaultmcp_conformance_debt` (bare `debt`), `obsidian_conformance_debt_render` → `vaultmcp_conformance_debt_render` (bare `debt_render`). The host publishes an external tool as `<sanitized publisher id>_<bare name>`, so the plugin id is the namespace; the bare names shed `obsidian_` (the host's namespace) and `conformance_` (already in the id). Breaking for any session or prompt that calls the old names. Reversal: the `id` in `manifest.json` (the shim reads it from there) and the bare names in `src/tools.ts`.

- **Scheme stayed in the host, and only the scheme KERNEL is shared.** The 2026-09-05 ruling keeps the scheme tools, the scheme Inbox pane and `jd:` addressing in the host (the `jd:` path syntax was retired on 2026-10-30). The scheme pack needs `schemeFindings`, `makeRegistry` and `DEFAULT_SCHEMES`, which moved to `@vault-mcp/core` first (#547) so this package imports them rather than reaching into the host. The vocab pack builds from `DEFAULT_VOCABULARIES`, as it did in the host. The scheme pack builds from the host's configured `schemes` since step (b) of 01.33 pick A (2026-10-30), because a fresh install has no scheme (`DEFAULT_SCHEMES` is empty): in the app, the host's live settings (`hostSchemes`, which include the machine-local override); in the CLI, the override's `schemes`, else the host's `data.json` (`cliSchemes`). No scheme configured: the scheme pack does not run, and a baseline that holds scheme debt is refused by the coverage check.

- **The allowlist posture is fail-closed on the whole surface.** Neither tool takes an argument in the host's `PATH_KEYS`: `debt`'s `folder` is a filter over findings (the run reads the whole vault), and `debt_render` takes no argument (its write target is configuration). That follows the provenance rule, "path-key iff it mutates the note it names". The host's F3 gate therefore refuses both under any active allowlist. In the host the report ran whole-vault under an allowlist (the #381 exception) and the render refused only when the register path was outside it. Both are now refused, which takes the last tool off issue #381's list. With no allowlist nothing changes. The render's own `out_of_allowlist` check is kept, now over the per-call `CallContext` (identity with no allowlist); under F3 it cannot fire today. Pinned by `publication: NOT ONE argument is a host path key`.

- **The guarded territories are the host's, read per run, and "cannot tell" refuses.** `main.ts` hands both sources the thunk `territoriesOrRefuse` (`src/host-lookup.ts`), which reads `api.guardedTerritories()` and throws when no host answers (absent, not loaded, too old). That is Governor's fail-closed reading of null, for the same reason: `[]` guards nothing and must never be what "cannot ask" means. The thunk is called inside the run, so the Drift pane shows the refusal and a tool call returns it as `Error: …`. Do not cache the list and do not keep a copy.

- **Settings adoption is a one-shot latch over two keys, and the host is never written.** `vaultConventions` (the host's top-level setting from #403) and `modules["conformance-debt"].config` (`staleAfterDays`, `debtBudget`, `strictBudget`, `registerDir`, `registerMaxRows`; a config row with no manifest, so no settings field existed in the host). Rules as in the other satellites: never write the host's settings, run once (`adoptedFromHost`), own values win. `hostSettings === undefined` means HOST NOT READY and holds the latch open (`!== undefined`, never a truthiness test); a throwing `saveData` holds it open too (`runAdoption`, injected save, pinned). The host keeps both keys in its data.json and reads neither (`conformance-debt` is in its `EXTRACTED_MODULE_IDS`).

- **A host record WITHOUT `vaultConventions` is not proof of a pre-#403 install any more.** The host stopped declaring the key when the rail left, so a fresh host's data.json lacks it too. `conventionsFromHostData` therefore takes the legacy seed only when the legacy baseline note exists in the vault, and is EMPTY otherwise (the `GOVERNOR_BASELINE_REL` override still fills the baseline). A host record WITH the key goes through `conventionsOnLoad` unchanged, #493 baseline seed included. The CLI's `pluginBaselineRel` reads this package's data.json first, then the host's by the same rule, so the CLI and the adoption cannot disagree.

- **`vaultConventions` is ABSENT from settings until it is known.** Set by the user, by the adoption, or by a stored record. While absent the rail reads EMPTY (`conventionsNow`), and the absence is what lets a late adoption still fill it. Do not default it into the stored record.

- **Config is read per call; the tools are re-published on every settings write.** `ConformanceToolsCtx.config` is a thunk. No description renders a config value today, so the republish is parity with the other satellites rather than a fix; keep it.

- **Refusals throw, and the envelopes are the host era's.** A refusal is a thrown `ConformanceRefusal` with a lowercase-snake `code`; the host renders `Error [code]: message`, byte-identical to the host's `codedError` for `invalid_register_dir`, `register_baseline_collision` and `out_of_allowlist`. A kernel throw (no baseline, a coverage refusal, a skipped-territory refusal) renders uncoded, as the host's `fail(e)` did; `AcceptForbiddenError` keeps `accept_forbidden`. One code is new, `invalid_argument`, because the boundary drops zod's `.min(1)` (only `type`, `description` and string `enum` survive `json-schema-to-zod.ts`), so the filters and `group_by` are re-checked in the handler.

- **The descriptions changed in one sentence each.** The allowlist sentence of each tool described the host's behaviour; it now says the host refuses the tool under an allowlist, which is what happens. The rest of each description is verbatim, except one sentence the debt tool gained on 2026-10-15 for the report cap (200 items, counts only past 5 MB).

- **The Drift pane's view type changed** (`vault-mcp-scheme-drift` → `vaultmcp-conformance-drift`; command `vaultmcp-conformance:open-drift`), because a view type and a command id are plugin-owned. A saved workspace drops the old leaf once. The pane is mounted for the plugin's lifetime (no module toggle now) and skipped when the host's headless mode is declared (`declaredHeadless`, the host's own rule read from its settings, else `VAULT_MCP_HEADLESS`).

- **Agents never mint acceptance here.** The report never writes; the render writes one derived note whose frontmatter is a `generated`/`generator` stamp, run through `registerAcceptRefusal` before every write. Acceptance metadata is minted only by the human-run `--rebaseline`, which refuses the live baseline. No tool carries an accept or approve verb.

- **The Forge replacements are rule packs, and every report has a size cap (2026-10-15).** Nelson verified "Replace the four Forge-only checks" on 2026-10-14 with the pick "A: in vaultmcp-conformance". Check (a) is the `shape` pack, check (b) is drift's K and L; (c) is a vault script and (d) has no repair rows, so neither is here. No new tool and no new finding shape (01.53 rule 6): the 00.92 severity rides in `detail`, and an unbound `type` is a `shape` finding (the plan put it in drift; it sits in `shape` so a blank `fileclassesRoot` cannot stop drift's E and J). `fileclassesRoot` is a scalar convention like the others: blank is dead and loud, and it is not seeded. The caps live in `report-caps.ts` (pure, imported by tools.ts) and `audit-output.ts` (the filesystem half): 200 findings and 256 KB for the register (a larger `registerMaxRows` is clamped; carried rows and cleared keys share the budget), 200 items for the debt tool's answer, counts only past 5 MB, `--findings-json` outside the vault only, and a `checked:` line on every report. The Forge code under `src/kernel/shapes/` is MIT, copyright Joshua Walls; keep `shapes/LICENSE` and the per-file notice with it.

## Build / test

- `npm run build` — esbuild, emits `main.js` (the CLI entry `src/kernel/main.ts` is not bundled; it keeps `import.meta` out of the CJS bundle).
- `npm test` — `pretest` builds `@vault-mcp/core`, then `tsc --noEmit && node --import tsx --test 'tests/*.test.mjs'`. The tests reach core through `packages/core/dist`, so the rebuild is load-bearing.
- `npm run conformance -- --root=<vault> …` — the standalone CLI (`node --import tsx src/kernel/main.ts`).
- Install for testing: copy `main.js` + `manifest.json` into `<vault>/.obsidian/plugins/vaultmcp-conformance/` and reload the plugin.

## Headless testing

Everything except `src/main.ts`, `src/settings-tab.ts` and `src/drift-pane.ts` is tested without Obsidian. The two Obsidian sources import `obsidian` as a type only, so their tests run them over a fake app pointed at a fixture vault. `tests/host-shim.mjs` reproduces what the host does to a published tool (the `<id>_<bare>` naming, `ok()`/`fail()` with the coded rendering, the annotations from an untrusted `readOnly` claim) and hands a handler the per-call `CallContext`; it does NOT reproduce F3, the allowlist, the queue, the journal or read-only mode, which are host code with host tests. Its `HOST_PATH_KEYS` is a snapshot for review, not a live tripwire: the host's `guard.test.mjs` is what fires when the host's key list changes.
