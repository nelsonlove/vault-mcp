# Vault MCP — the Governor suite's HOST (plugin id `vault-mcp`) — architecture & working notes for Claude Code

An Obsidian plugin (id `vault-mcp`; `governor` between 0.12.0 and the suite split's S3c) embedding an MCP server with direct `app.*` access, reached by Claude Code via a Unix socket + bundled stdio bridge. **This package is the HOST half of the suite split.** The governance provider — proposals, admission, mandates, the standing chain, the review pane — is `packages/governor`, a separate Obsidian plugin that plugs in through the seam (`src/mcp/seam.ts`) and publishes its tools through `vault-mcp-api` like any other publisher. With no provider installed every seam consultation is vacuous and this plugin is a complete product: audited, journaled, allowlist-scoped vault access over MCP. Local-with-Obsidian counterpart to the remote, filesystem-only `obsidian-vault-mcp-server` (JD 92046). Design specs and implementation plans live in the vault at `00-09 System/00 System management/00.89 vault-mcp/` (the slot was `07.36 obsidian-governor` from 2026-08-19, and took the repo's name `vault-mcp` on 2026-10-08; the `06.20 obsidian-vault-mcp-plugin` slot it replaced, and the older JD 92050 one, are both retired).

## Locked decisions (don't relitigate without reason)

- **Naming.** The product/project/framework is **Governor** — the SUITE. Since the split (S3c) that name belongs to the governance PROVIDER plugin, and **this plugin's id is `vault-mcp` again**, migrated back with the same machinery that moved it the other way at 0.12.0. Two things deliberately did NOT follow the id, each because it is a name something else already depends on: the **npm names** `@vault-mcp/core` and `vault-mcp-api` are unchanged, and the **five governance tool names** keep their exact spellings through the host's closed grandfather table (below). The acceptance capability's module id is `acceptance` (migrated from `governance`; a legacy `modules.governance` settings row is adopted once by `migrateLegacyModuleIds`). **Deliberately historical, do NOT rename:** the shipped always-on tool names `governance_revisions` / `governance_submit_revision` (renaming shipped tool names breaks agent sessions for zero semantic gain), the `@vault-mcp/core` workspace package name, and the on-disk state dir `<plugin dir>/governance/` (its files are live operator state; moving them is an S3 migration item, not a rename). (**The source dirs came OFF this list in S1** — the suite split, adopted by Nelson 2026-08-25, needs the host/governor boundary to be structural, so `src/kernel/governance/` → `src/governor/kernel/` and `src/governance/` → `src/governor/wiring/`. The old entry's reasoning — "churns every import for zero user-visible gain" — held while the two halves shipped as one plugin; §2 of `docs/suite-split-design.md` makes them two, and the churn is the point.) (The local directory name WAS on this list; Nelson reversed that on 2026-08-19 and renamed it to `obsidian-governor` to match the remote — a repo slot is named after the repository. The repo was renamed again, to `obsidian-mcp-suite` and on 2026-10-08 to `vault-mcp`, so `~/repos/system/vault-mcp` is the path; the old `~/repos/obsidian-vault-mcp-plugin` survives only as a convenience symlink.) Env vars are `GOVERNOR_*` with the `ASSENT_*` spelling accepted as a fallback alias (GOVERNOR_ wins when both are set).

- **THE CLAUDE CODE MCP SERVER NAME IS `vault-mcp` AGAIN — the wire rename (Nelson's ruling, 2026-09-09).** Client-visible tool prefixes are `mcp__vault-mcp__*`. The split deferred this deliberately and the entry above said the server name "stays `governor`"; Nelson ruled the other way and this bullet supersedes it. The reasoning is the pending-review rename's, one level up: **post-split, prefixing the HOST's whole tool surface with the PROVIDER's id is the same architectural lie** `obsidian_pending_review` → `governance_pending_review` fixed at tool level. `governor` names the governance provider; the socket, the guard, the kernel and every `obsidian_*` tool are the host's, and a handshake that introduced them as `governor` said otherwise on every call. The deferred entry's counter-argument — "the client-visible prefix is a shipped name" — was the correct default and lost to a stated cost, not to a hand-wave: **the cost is one-time and it is an operator's `mcp__governor__*` permission entries needing re-adding as `mcp__vault-mcp__*`**, named to Nelson and accepted. Nothing else breaks: MCP tools are discovered per session, and a pre-cutover `claude mcp` entry named `governor` keeps working untouched, because the bridge resolves the socket from the discovery jsons and never from the registration name. Three names carry it, each pinned in `packages/host/tests/wire-name.test.mjs`: `MCP_SERVER_NAME` (`src/claude-cli.ts`) is what `claude mcp add` registers, `SERVER_INFO_NAME`/`serverInfo()` (`src/mcp/helpers.ts`) is what the `initialize` handshake declares, and `buildRegisterCommand` (`src/register-command.ts`) — the paste-by-hand twin — now IMPORTS the constant instead of spelling it again, which is how the two drifted apart in the first place. **The grace state is DISCLOSED, not smuggled:** `claudeIsRegistered` asks about the new name ONLY, so a vault still carrying just the old entry reads "Registered: no"; a separate `claudeLegacyIsRegistered` probe puts "a legacy 'governor' registration is still present" beside it in the settings tab with the `claude mcp remove governor` line. Accepting either name in one probe was rejected explicitly — 0.12.0's dual-id pattern is for the state DIRS, where silent continuity is the point, and a half-migrated registration reading as clean is the failure mode this split's reviews kept finding. **`mcp__governor__*` stays in the cc-plugin hook matcher** (`mcp__(vault-mcp|governor)__.*`), for the same grace reason. Spelling, because it is easy to get wrong: Claude Code does NOT sanitize the hyphen out of a server name (`mcp__omnifocus-enhanced__*`, `mcp__claude-in-chrome__*` in any live session), so the prefix is `mcp__vault-mcp__*` — the exact spelling this server used before 0.12.0 — never `mcp__vault_mcp__*`.

- **THE SPLIT IS DONE (S3c): two plugins, and this package is the host.** `src/governor/` — the two subtrees S1 created — is GONE from this tree; `src/governor/kernel/` is `packages/governor/src/kernel/` and `src/governor/wiring/` is `packages/governor/src/wiring/`. **Everything under this `src/` is host.** The enforcement is now the package boundary itself: `packages/host` has no dependency on `packages/governor` and no path to it, so a host file importing provider code does not typecheck and does not bundle. `tests/host-governor-boundary.test.mjs` — which enumerated the crossings and shrank 45 → 32 → 30 → 27 across S1–S3b — was DELETED rather than kept, because its scan matched relative specifiers only and would have reported zero across packages and passed vacuously forever. `tests/host-layering.test.mjs` replaces it with what the package boundary does not catch: a relative specifier escaping `packages/host/src` (which resolves and bundles in a monorepo), and any surviving reference to the retired in-tree addresses. Do not reintroduce `src/governor/`, `src/governance/` or `src/kernel/governance/`.

- **What the provider took, and the four things published so it could.** It took `src/governor/**`, the three tool files (`tools-governance-mandate.ts`, `tools-governance-revision.ts`, `tools-pending-review.ts`, now `packages/governor/src/tools/`), the `acceptance` module row, the local-history settings, and the `wp8-cutover-runbook.md`. Four contracts were PUBLISHED into `@vault-mcp/core` rather than forked, on the `isVisible` / `resolveScope` / `scanForAcceptFence` precedent — each because a second copy would be a correctness bug rather than a duplication: **`splitSettings`** (which `data.json` key belongs to which plugin — a key both claim gets each plugin's save overwriting the other's edit, a key neither claims is dropped on the first save), **`CHANGE_CLASSES`** (its canonical ORDER is what two producers hash a proposal subject over; a drifted copy forks the standing chain), **`NOTE_WRITE_ACTION`** (the id, version and declared classes the provider's write observer speaks for; two copies let the host bump the version while the provider quietly stopped proposing), and **`vaultSlug`** (the host names the socket by it and the provider names the standing chain's git directory by it — a one-character disagreement reads as "chain absent here" on the machine that is holding the chain). `src/kernel/operations/action.ts` and `src/paths.ts` re-export theirs, so no call site here moved.

- **THE GRANDFATHER TABLE (`src/mcp/external-tools.ts`), and it is CLOSED.** An external tool publishes as `<sanitized owner id>_<bare name>`, and every satellite extraction has paid that rename tax deliberately — the plugin id IS the tool namespace. Four names could not: `governance_revisions`, `governance_submit_revision`, `governance_mandate_draft` and `governance_mandates` were on the wire when the split happened, and renaming a shipped tool name breaks agent sessions for zero semantic gain. So `GRANDFATHERED_TOOL_NAMES` maps each of those four to the single owner id (`governor`) allowed to publish it unprefixed. **A host-held table, never a flag on the spec:** an `exactName: true` flag would be publisher-controlled, so any plugin could claim any name. It is also gated on the id the TABLE names rather than on `seam.providerIds()`, because gating on "whoever holds a seam registration" would let any plugin that registers a write observer claim a locked spelling. Nothing is added here; a new tool takes the ordinary namespaced form.

- **IT CARVES OUT THE PREFIX RULE AND NOTHING ELSE — `obsidian_pending_review` was RENAMED to `governance_pending_review` instead (Nelson's ruling, 2026-09-08).** The table's first draft also held the pending-review tool, which would have made it a carve-out from **F1**, the refusal of any published name beginning `obsidian_`. Nelson ruled against that and took the rename. Three reasons, and they bind whatever comes here next: **(1)** an F1 exception, even one gated on a provider id, permanently weakens a NAMESPACE-INTEGRITY rule and becomes the precedent for the next exception — the rule is worth more than one name's continuity; **(2)** the locked decision forbids renaming shipped tool names *for zero semantic gain*, and this rename HAS semantic gain, because the `obsidian_` prefix branded a governance tool as a host built-in, which after the split is an architectural lie, while `governance_pending_review` says what the tool is and matches its two siblings; **(3)** the breakage is near zero — MCP tools are discovered per session, and the one glob that patterns on the old spelling (`cc-plugin`'s `*pending_review*`) still matches. So F1 is UNCONDITIONAL in the code, no entry in the table may begin `obsidian_`, and **no dormant exception machinery ships**. `obsidian_pending_review` comes OFF the do-not-rename list with this ruling; `governance_revisions` and `governance_submit_revision` stay on it.

- **The cost the five published tools pay instead, and it is the same one every satellite paid.** As external tools their read-only claims are DISTRUSTED unless the operator lists `governor` in `trustedReadOnlyPlugins`, and under an active path allowlist the F3 gate blocks any external tool carrying no recognized path key — so four of the five are refused wholesale while an allowlist is active, and only `governance_submit_revision` (which takes `path`) stays scoped per-path. They also lost their in-tool `isVisible` filtering, because a satellite cannot reach this host's guard settings; the seams are kept dormant in the provider so an apiVersion-2 SDK carrying caller scope wakes them with no code change. One further loss, named because it is a real regression rather than a tightening: **`governance_mandate_draft` can no longer default `delegate` to the calling connection's session**, because a published tool does not learn which connection is calling. It refuses `no_session` instead.

- **THE GOVERNANCE SEAM (`src/mcp/seam.ts`, S2 of the suite split).** The host's hook API for an optional governance provider, built and consumed IN-TREE — still one plugin artifact, so the seam's sufficiency is proven at zero distribution risk. It ships on the same `plugin.api` object `external-tools.ts` defines (the seam's methods were additive and left `apiVersion` at 1; since SDK 1.1.0 (#402 step A) the SDK treats the number as a FLOOR, and step B bumped it to **2** for the partial-result envelope and the per-call `CallContext`, so a satellite rebuilt against that SDK keeps registering).
  - **Two hook classes, and there will never be a third.** `registerWriteObserver(id, observe)` — post-write, observe-only, the host ignores the return value. `registerSessionRefusal(id, refuse)` — consulted at dequeue, returns `{code, detail} | null`. **Refusal-shaped, never boolean:** `null` is *silence*, not an allow, so the type cannot express permission and a registrant cannot un-refuse what the host or another registrant refused. Anything that could mutate a write in flight or assert acceptance is the class the seam must never offer.
  - **No `registerWriteVeto`.** §5 sketched one; S2 looked for a real registrant and found none (the fuller accept-transition guard is host-side in `@vault-mcp/core`, and the legacy-writer guard is a provider-internal `BaselineStore` predicate off the MCP write path). Unused perimeter surface is dead code. It lands when something needs it, with its round-trip test.
  - **Disposer-only revocation.** Every `register*` returns a disposer and the disposer is the ONLY address; `id` is a diagnostic label and an owner name, never an address. Same fix applied to `ExternalToolRegistry`: **`unregisterTools(ownerPluginId)` is GONE** from the host and from the `vault-mcp-api` SDK — it let any caller holding the api object revoke any publisher's tools. The SDK always used the disposer, so publishers are unaffected.
  - **Hook lists are module-private**, in a WeakMap keyed by a token only `createGovernanceSeam`'s two returned objects hold (the `governor/wiring/wiring.ts` pattern). `main.ts`'s external-tool registry and seam moved into module-level WeakMaps for the same reason — a `private` class field is compile-time privacy only, so `app.plugins.plugins.governor.externalRegistry` was walkable. Registration stays reachable and that is fine; the LIST of what everyone else registered must not be.
  - **Budgets.** The session refusal runs inside the kernel's queued closure (where `sessionLive` ran), so `WRITE_TIMEOUT_MS` bounds it. The one exception is the `"rotate"` check (#568, `kernel/sessions/connection-session.ts`): it runs before a mutation is queued, so it carries its own `WRITE_TIMEOUT_MS` timer, and a timeout counts as a refusal (no rotation). Observers are dispatched OFF the caller's result path — one `queueMicrotask` per hook, every failure caught — so a hanging or throwing observer cannot cost a caller a write that already landed. `WriteFacts` deep-freezes `operation` and `actor`; bytes are deliberately NOT copied per hook (§0's threat model excludes the actor a copy would defend against).
  - **What S2 moved.** The `propose` block left `mcp/server.ts` for `src/governor/wiring/write-observer.ts` behind the observer hook; the host keeps only the write-facts slot and `reportCompletedWrite`'s attribution guard. Session liveness is now the host's own expiry floor (`expiryRefusal`, `src/kernel/sessions/session.ts`) composed with the seam's refusal — **the session contract is HOST-owned** (the host mints; a session is transport state) while the session STORE and its revocation state stay with the provider. `ServerCtx` therefore names **zero** provider types, which is S2's exit criterion; provider tools arrive as `BuildOpts.providerTools` registrars from the composition root instead of as ports on the host's context. `mountAction` moved to `src/mount-state.ts` (the host drives the scheme panes with it too).
  - **Condition 6:** `obsidian_plugin_toggle` and `obsidian_plugin_uninstall` refuse a **registered governance provider's id**, the same way they already refuse the host's own — an agent doing cleanup must not be one call away from switching off the thing that reviews it. Simple refusal, not the persisted latch (that is on `reference/hostile-threat-model`).

- **Transport: Unix socket + bundled bridge.** Not HTTP. The `chmod 600` socket is the *only* auth boundary — no token, no listening TCP port (a localhost port is reachable by any local process and by browser DNS-rebinding; the socket isn't). `bridge.mjs` is built by esbuild and **embedded into `main.js`** via `define` (`__BRIDGE_SOURCE__` → `src/bridge-asset.ts`), then written to `~/.claude/vault-mcp/` on load (plus a grace-period copy at the 0.12.0-era `~/.claude/governor/`). **The two dirs swapped roles at S3c** — between 0.12.0 and the split `~/.claude/governor/` was canonical, which is what this line said until 2026-09-08; `src/paths.ts` is authoritative (`stateDir()` / `legacyStateDir()`). Never ship the bridge as a separate npm install. The bridge survives Obsidian restarts/plugin reloads: it captures the client's `initialize` handshake and, when the socket drops, fails in-flight requests, queues new ones, waits for the socket to return (`VAULT_MCP_RECONNECT_MS`, default 5 min), then replays the handshake to the fresh per-connection server and swallows the duplicate response.
- **Multi-client transport.** `UnixSocketListener` accepts each connection and `main.ts` builds a **fresh `McpServer` per connection** (`buildMcpServer`). So concurrent Claude Code sessions / background agents don't evict each other, and *conditional registration at build time is the dynamic-registration mechanism* — there is no `app.plugins.on("change")` + `tools/list_changed` machinery (obviated; new tools appear on session reconnect).
- **Per-connection options ride a preamble line** (`src/preamble.ts`, shared like ndjson.ts). The bridge may send `{"vault_mcp_preamble":1,…}` as the connection's FIRST line (on every attach, including reconnects — each connection is a fresh server); the listener peeks the first line and consumes it, passing anything else through untouched (old bridges stay wire-compatible — no preamble means default options). The reverse direction is gated too: the bridge sends the preamble only when the vault's discovery advertises `capabilities: ["preamble"]` — a newer bridge meeting an older plugin (the shared `bridge.mjs` is rewritten by whichever vault loaded last) warns on stderr and falls back to the full surface instead of feeding the old listener a bogus first message. Currently carries `code_mode`: capture all guarded registrations into a registry and expose only `obsidian_search_tools` / `obsidian_describe_tool` / `obsidian_call_tool` (`tools-code-mode.ts`). The meta-tools register UNguarded — the captured handlers carry the guard, so enforcement lands on the target call (guarding `obsidian_call_tool` itself would make read-only mode block reads).
- **State namespace: `~/.claude/vault-mcp/`** holds `bridge.mjs`, `<vault-slug>.sock`, `<vault-slug>.json` and `observations/<vault-slug>/`. Resolve `~` via `os.homedir()`. The 0.12.0-era `~/.claude/governor/` dir also gets the bridge plus a `legacy: true` discovery copy pointing at the NEW socket (old registrations keep working); the bridge and the connect plugin's health probe read both dirs and skip `legacy` duplicates. **The FLAG decides which entry is the duplicate, never the directory** — both readers keyed the skip to one hard-coded dir until the S3c wire rename, on the 0.12.0-era assumption that `governor` was canonical, which the split inverted, so post-split a single open vault was read twice (unflagged from `~/.claude/vault-mcp/`, flagged from `~/.claude/governor/`) and the bridge failed it as "multiple vaults open; specify --vault". A flagged copy always has an unflagged twin on disk, so skipping flagged entries in EVERY dir is correct in every era and survives the next flip. Pinned in `packages/host/tests/bridge.test.mjs`. **The namespace has moved twice, with the id, and it moved BACK at S3c** — the pre-S3c reading of this line (`governor` canonical, `vault-mcp` legacy) is the history, not the current fact. One thing does NOT follow the host: the governance provider's standing-chain repository stays at `~/.claude/governor/history/<slug>/`, because the provider keeps that id, so the two plugins share that directory writing disjoint names.
- **Never write `~/.claude.json` directly.** Registration goes only through spawning the `claude` binary (`claudeRegister` in `src/claude-cli.ts`). When spawning `claude`, augment PATH (`spawnEnv`) — Obsidian's GUI PATH is minimal and the `claude` launcher shim runs `#!/usr/bin/env node`.
- **Plugin-gated tools gate on the LOADED instance** (`app.plugins.plugins[id]`), not `app.plugins.enabledPlugins` — `enabledPlugins` can list a configured-but-uninstalled plugin (stale entry).
- **`ok()` returns both `content` (text) and `structuredContent`.** `fail()` returns `isError: true`. `okError()` is ok()'s shape plus `isError: true` — for batch tools whose structured per-item report must survive a total failure (fail() would flatten it to text). Match the 92046 shapes; tool names are the identical `obsidian_*` set (strict-superset).
- **Safety guard** (`src/guard.ts`) is applied by monkey-patching `server.registerTool` in `buildMcpServer` (single interception point). A tool is mutating iff `annotations.readOnlyHint === false`. Read-only mode blocks mutating tools; the path allowlist normalizes paths (`posix.normalize`, reject `..` escapes) before prefix-matching. The wrapper itself lives in `src/mcp/guarded.ts` (`makeGuarded`) — separate from `server.ts` so it pulls in nothing from `obsidian` and is unit-testable.
- **Kernel v0** (`src/kernel/`) — the Assent kernel's first capabilities, shipped as transport hardening. They all bind at the SAME interception point as the guard, keyed on the same `readOnlyHint === false` discriminant, so "guarded", "serialized", "journaled", "conditional" and "idempotent" are one set by construction.
  - **Serialized write queue** (`write-queue.ts`) — every mutating call runs through one FIFO queue; reads never queue. The queue is a **plugin singleton** created in `main.ts` and carried into each per-connection server via `ServerCtx.kernel` — per-connection would serialize nothing, since concurrent sessions are the whole point. Each operation gets `WRITE_TIMEOUT_MS` (30s, constant, not a setting); on expiry that operation is **abandoned** (Obsidian exposes no cancellation) and fails with a typed `WriteTimeoutError` rendered as `Error [write_timeout]: …`, and the queue runs the next one. The bridge must never wedge behind one stuck call. **At unload the queue CLOSES** (#435, `this.register(() => writeQueue.close())` in main.ts): every operation still WAITING is refused `Error [plugin_unloaded]` (never ran, safe to retry) and later calls are refused too, including an item already dequeued whose fn has not started; the one RUNNING cannot be cancelled and settles on its own. The refusal reaches the journal and in-process callers; a socket caller sees its connection drop, because unload closes the listener in the same step. Before this, a reload left the old instance's queue running, and its waiting writes landed minutes later outside the new instance's key store. Non-reentrant: in Code Mode `obsidian_call_tool` registers unguarded, so only its target takes a slot.
  - **Write journal** (`journal.ts`) — one JSONL record per mutating operation in `.obsidian/plugins/vault-mcp/journal/YYYY-MM.jsonl` (UTC month, so filenames agree with record `ts`). It was `plugins/governor/journal/` between 0.12.0 and S3c; the host COPIES that directory out once at adoption — see `src/id-migration.ts` — and never writes into the provider's folder again. Operation-centric: `{ts, op, target{path,uid,paths,ref}, actor{transport,client,connection,server?{vault,install,version}}, argsDigest, outcome, error?, durationMs, queueWaitMs, revBefore?, revAfter?, corrects?, ifRev?, idempotencyKey?, intent?, addressedAs?, syncWarning?, dedupeOf?, lockNotice?, effects?}` (`outcome`: `ok|error|late-ok|late-error|conflict|deduped`). `addressedAs` (issue #91) is audit-of-intent beside `target`'s audit-of-effect: when a mutating call addressed by `uid:<v>`/`jd:<addr>`, the record carries `[{ref, path}]` — the form the caller used and what it resolved to at the interception point (enqueue-time call metadata like `argsDigest`, capped like `target.paths`, kept on deduped terminals like `intent`, absent for plain-path calls). **Append-only** — `append` is the only write path and no edit/delete/prune API exists. `target`, `revBefore` and the clock all sample **at dequeue**, inside the queued closure (an enqueue-time probe describes the operation ahead of you); `durationMs` is handler time, `queueWaitMs` is enqueue→dequeue. `target.ref` (`command:<id>`, `plugin:<id>`, …) is derived from well-known argument keys in `mcp/guarded.ts` (`REF_KEYS`, ordered most-identifying-first so an `id` outranks a `name`) — a fallback for pathless mutators, never overriding a real path; deliberately un-namespaced, since `op` already disambiguates two tools sharing an argument name. Because records are never rewritten, an abandoned operation that settles after its timeout appends a **corrective record** (`outcome: late-ok|late-error`, `corrects: <original ts>`, fresh `revAfter`) via the queue's `onLate` hook. Note bodies never land: `digestArgs` summarizes body keys and long strings as `<N chars>`. Journal failures `console.error` and are swallowed — a broken journal must never fail a vault operation. `uid` (frontmatter) and `rev` (mtime) come from `TargetProbe` (`obsidian-probe.ts`, the only kernel file that imports `obsidian`). A **throwing probe** never masks a result: at dequeue it fails the call as `ProbeError` (message prefixed `probe:` so the journal doesn't blame the vault operation), and on the record-only paths (`revAfter` in `finally` and in `onLate`, `uid` on terminal records) it is swallowed and the field is simply absent. `syncWarning` (the Sync guard, #507) is the guard's warning when a write went on while this Mac's Obsidian Sync was behind or unreadable; journal-only like `intent`, not part of idempotency identity, and kept on deduped terminals too.
  - **`intent`** (B2) — the third kernel argument: advisory agent-authored "why" text on any mutating call, declared/peeled exactly like `if_rev` (handlers never see it, so it structurally cannot reach note frontmatter). **Journal-only**: recorded verbatim on the record beside op/actor (`JournalRecord.intent`) for review surfaces to display as "agent says" — never trusted, never interpreted, NEVER an acceptance signal (nothing in the kernel reads it back). Deliberately NOT part of idempotency identity (unlike `if_rev`): advisory text doesn't change what was written, so a replay may reword it and every record — including `deduped` terminals, unlike `ifRev` — keeps its own call's text. Degrades quietly without a kernel (peeled and dropped; nothing destructive about losing a description). Max 2000 chars.
  - **`if_rev` + `idempotency_key`** — kernel arguments, not tool arguments. `withKernelArgs` (`mcp/guarded.ts`) adds both to the `inputSchema` of every MUTATING registration at the interception point — mandatory, not decoration: the SDK parses args with `z.object`, which STRIPS undeclared keys, so an undeclared `if_rev` would never reach the wrapper. `makeGuarded` peels both off the args (handlers never see them) and passes them to `Kernel.runMutation` as `MutationContext.ifRev` / `.idempotencyKey`. `if_rev` is compared to the live rev **at dequeue**, in the same closure that samples `revBefore` — an enqueue-time check compares against the world the operations ahead of you already changed, which is the lost update the feature exists to catch. Mismatch ⇒ `RevConflictError` ⇒ `Error [rev_conflict]: …`, no write, journal `outcome: "conflict"`. Unreadable rev (missing file, no probe) fails closed. Multi-target ops check the FIRST target — for a move that is the SOURCE (`from` is declared before `to`, and `collectPaths` walks in declaration order; pinned by a test). **With no kernel** (`opts.kernel` absent — tests, bare embeds) a mutating call carrying `if_rev` is REFUSED (`Error [precondition_unsupported]`) rather than written unconditionally: an unenforceable precondition must not fail open. `idempotency_key` degrades quietly there instead, because its failure mode is at-least-once rather than destructive. Idempotency (`kernel/idempotency.ts`) is settled BEFORE the queue, and the key is **reserved at entry** (`IdempotencyStore.claim` — a synchronous check-and-set, no await in between, so concurrent retries cannot all become owner): one caller runs, the rest await its settlement and return the SAME envelope (journal `outcome: "deduped"`, `dedupeOf` = winner's `ts`) without a queue slot. **Waiters share the winner's outcome whatever it is** — a thrown failure is rethrown to all of them; only AFTER settlement does a thrown failure leave the key free for FUTURE calls. Key identity is (key, op, **args**, **kernel args**): a divergent op, divergent args, or a divergent — including newly present/absent — `if_rev` is `IdempotencyMismatchError` (`reason: "op" | "args" | "if_rev"`), never a silent replay that would discard a write while reporting success. `if_rev` is checked at claim time rather than folded into the args fingerprint, so the failure can name which half diverged and both revisions; the precondition is half of what the caller asked for, and replaying across it would assert a check that never ran. The args fingerprint (`fingerprintArgs`) is the stable-serialized `argsDigest` PLUS a hash of the full args — the digest collapses bodies to `<N chars>`, so equal-length bodies would otherwise collide. TTL 10 min, LRU cap 500, in memory — ONE STORE PER VAULT on `globalThis.__vaultMcpIdempotencyV1` (bump the version when the store class changes shape, so a new build never adopts an old object), handed to each new instance at load (#435), so a reload keeps every key, including the RESERVATION of a write still running on the unloaded instance (a same-key retry waits for it). Obsidian-free like every other kernel module: it is defined over an injected `UidSource` (`paths()`, `uidOf(path)`); the adapter is `obsidianUidSource` in `obsidian-probe.ts` and the events are wired in `main.ts` (`wireUidIndex`) — `workspace.onLayoutReady` → `rebuild()` (before that the cache is still warming), then `metadataCache.on("changed")` → `onChanged` (covers uid added / changed / removed, and note creation), `vault.on("rename")` → `onRenamed`, `vault.on("delete")` → `onDeleted`, all via `registerEvent`. `onLayoutReady` takes a plain callback and returns no EventRef, so it is gated on a **disposed flag flipped by `this.register`** instead — an unload before layout must not rebuild an index for an instance that is gone. The whole wiring is **gated on `settings.enabled`**: with the socket down nothing can address a uid, so maintaining the index off every metadata event is work for no reader. **Duplicates are kept, never fixed**: a uid maps to ALL its paths in precedence order — `rebuild` sorts AND incremental `add` inserts in sorted position, so precedence is a property of the vault rather than of cache-warming or edit order (`onRenamed`'s in-place replacement is the one documented exception, and it is deliberate: a rename must not demote the note the uid currently resolves to) — `duplicates()` makes them queryable, and `requireOne` — the only resolution addressing may use — throws `UidAmbiguousError` rather than picking. Files with no uid are absent from the index entirely. `onRenamed` replaces the mapping IN PLACE (preserving a duplicate's precedence) and prefers what the index already knew to `source.uidOf(to)`, because at rename time the cache may not have re-keyed yet. The kernel takes `target.uid` from the index first and falls back to the `TargetProbe` frontmatter probe, so a uid lands on the record even when the cache is behind. `obsidian_resolve_uid` (read-only) is the lookup in both directions plus a no-argument duplicates report; it is **allowlist-filtered**, since an unfiltered index would be a path oracle for the area a sandboxed session is excluded from. The filter itself is `visiblePaths` in `guard.ts` (hoisted out of tools-uid.ts) because **uid ADDRESSING decides over the same set** — see below.
  - **uid addressing** (`uid:<value>`) — any path-bearing argument accepts `uid:<value>` and is rewritten to the real path in `makeGuarded`, BEFORE `guardCall`, for **reads and writes alike** (the guard wraps every registration, so one spot covers both — there is no separate read path). Per-tool support was never on the table: like the kernel args, the next path-taking tool would forget. It is defined over `mapPaths` in `guard.ts` — the walker `collectPaths` is now itself defined over — so the addressable set and the allowlist-scoped set are one set by construction. `mapPaths` returns the SAME object when nothing changed, so a call using no uid addressing behaves identically byte-for-byte. Resolution runs before the guard so the allowlist checks the RESOLVED path (a uid must not be a sandbox bypass); the resulting disclosure risk is closed by `uidSafe`, which folds resolved paths back to their `uid:` form in the refusal text. Unresolvable ⇒ `Error [uid_unresolved]`, ambiguous ⇒ `Error [uid_ambiguous]` naming the candidates; both refuse before the handler, before the queue, and are not journaled (nothing ran). **The candidate set is the allowlist-VISIBLE one** (`requireOne(uid, settings)` over `visiblePaths`, the same helper `obsidian_resolve_uid` uses): 0 visible ⇒ unresolved even when hidden carriers exist, 1 visible ⇒ resolve to it, 2+ visible ⇒ ambiguous naming only those. This is load-bearing and must not regress — `uid_ambiguous` used to name EVERY carrier, so a session sandboxed to `Projects/` learned an `Archive/…` path just by addressing a duplicated uid, which is the exact oracle `visible()` exists to close (`uidSafe` could not help: the leak was in the uid error, not the guard's). It also keeps the lookup and the addressing from disagreeing about what a uid names — they did before, the lookup resolving a duplicate the addressing refused. A consequence: a uid carried only outside the allowlist now refuses as `uid_unresolved` rather than `out_of_allowlist`, which is also less disclosure (it does not confirm the uid exists). No index ⇒ fail closed, never "treat it as a filename". `obsidian_resolve_uid`'s no-argument TOTALS are visible-filtered too (`UidIndex.indexedPaths()` → `visiblePaths`, then a Set for the uid count) — raw `size`/`uidCount` told a sandboxed session how much lives outside its allowlist, a cardinality oracle beside the path oracle. `visiblePaths` returns the SAME array when no allowlist is active, so the unfiltered case still reads the index's own counters.
  - **Scope-provider module** (`kernel/scheme/`, chapter 6's `ScopeProvider` made concrete) — scope resolution and placement as the core, addressing and allocation as capability flags (`provider.ts`: `{validate: true; itemAddresses; allocate; ordered}`), so a scheme whose grammar names classification tokens rather than item identities (GTD/PARA — routed elsewhere, not built here) still fits without contortion. `jd.ts` is the first (and so far only) provider — Johnny Decimal grammar ported verbatim from `obsidian-johnny-decimal`'s `jdId.ts` (areas, categories, `XX.YY`/`XX.YYY`, 5-digit expanded areas/categories, fractal ids). `registry.ts` is the `SchemeRegistry`: named instances (`{id, provider, config}` from settings, default one `jd` instance) plus address-string resolution (`jd:06.11` → path). **Config is not hardwired** (Nelson's ruling): each instance's `config` is a partial override deep-merged at the key level over that provider's own defaults, and is a **per-provider namespace validated by the provider itself** (`validateJdConfig` for `"johnny-decimal"`) — an unknown provider name or a config that fails validation **skips that one instance and logs**, rather than failing the whole registry or trusting an unvalidated shape. `findings.ts` is the pure conformance rule core (misfiled / duplicate_address / malformed_name / unaddressed, plus the name-hygiene codes `name_colon` / `name_trailing_space` folded in from obsidian-jd-numbering's `checkNote` lint — the two of its checks scheme lacked and could express purely over a filename; the hygiene codes are emitted by `validateName` alongside `malformed_name` but never suppress `unaddressed`, since a name can carry an address AND a trailing space) — the whole-vault `schemeFindings` is **deliberately NOT registered as a tool**: per the Conformance README's "capabilities arrive as rule packs, never as new surface," it is rail material a later task mounts, not something this module exposes itself (the per-name `validateName`, by contrast, IS exposed one-name-at-a-time as `obsidian_validate_name` — see the scope-tools bullet). jd-numbering's remaining lint checks were NOT folded: malformed/duplicate/folder-mismatch(→misfiled)/missing-id(→unaddressed) are already covered model-appropriately, and its frontmatter/tag-dependent checks (filename↔frontmatter mismatch, folder-note-id, redirect-on-zero) cannot be expressed in this path-canonical model, which — unlike jd-numbering's frontmatter-canonical `jd-id` — reads only the filename token and never frontmatter. Allocation (`nextFree`) already matches jd-numbering's assign-next for normal and expanded-category scopes; the two DIVERGE only on expanded-AREA numbering (jd-numbering allocates a per-category `<cc><3-digit>` space via the category scope; scheme allocates a per-band `<d><4-digit>` space via the area scope and refuses category-scoped allocation in an expanded area) — scheme is canonical, so `nextFree` was left unchanged and the divergence surfaced for adjudication. Each instance also carries an optional **`excludedRoots`** (`SchemeInstanceConfig.excludedRoots`, sibling of `config` — instance-level and provider-agnostic, validated and skip-and-report'd the same way as an invalid provider config): vault-relative folder prefixes that instance never resolves, lists, or claims, applied uniformly via `excludeRoots` (registry.ts) at every listing site — tools-scheme.ts's per-call visible listing, `resolveSchemeArgs`'s `jd:<address>` addressing, and `schemeFindings` — so territory like an archive tree that reuses a live-spine address stops colliding with it, without renaming anything; it bounds scheme resolution only, never general path access to the excluded notes themselves. **Three mutating tools** (`mcp/tools-scheme-write.ts`, the write half completing the module: `obsidian_assign_address`, `obsidian_refile_address`, `obsidian_renumber_address`) are thin PLAN-then-APPLY shells over a pure planning core (`kernel/scheme/mutate.ts`'s `planAssign`/`planRefile`/`planRenumber`, returning `AssignOutcome`/`RefileOutcome`/`RenumberOutcome` built from a shared `MoveStep` shape) — nothing in the tool layer recomputes "what should move where", it only decides whether to preview (`dry_run: true`, mandatory on all three, no default) or execute via `moveOne` (`tools-vault-write.ts`'s move primitive, reused rather than re-implemented, so these inherit the same link healing as `obsidian_move_notes`). `obsidian_assign_address` takes `{path, scope, scheme?, dry_run}` and assigns the next free address in that scope — the same answer `obsidian_next_address` would compute for the same scope right now — and never overwrites, since planning always targets a FREE address, so a race where something now occupies the computed path fails the move rather than clobbering it. `obsidian_refile_address` takes `{path, dry_run}` with no `scope`/`scheme` argument (the note's own address, resolved against whichever configured instance recognizes it, decides both); already-correctly-filed reports `already_correct: true` with no move regardless of `dry_run`, closing the loop `obsidian_expected_location`'s `placed: false` opens. `obsidian_renumber_address` takes `{path, to_address, scheme?, dry_run, on_occupied, displace_to_address?}` and moves a note to a specific target address parsed through the resolved instance's own grammar (`provider.parse`, not a bare string guess); named `to_address`/`displace_to_address` rather than `to`/`displace_to` — `to`/`from` are well-known path-argument names in `guard.ts`'s `PATH_KEYS`, so under the original `to`/`displace_to` naming an active path allowlist checked the ADDRESS STRING as if it were a path and refused calls whose actual `path` argument was fully inside the allowlist; renaming was cheap since the tool was not yet released. `on_occupied` (`"fail"` default / `"auto"` / `"manual"`) is the explicit choice replacing what would otherwise be an interactive occupant-displacement prompt — `"fail"` refuses when `to_address` is occupied (and is a no-op success, not a "occupied" error, when the occupant IS the source note itself — a retry of an already-applied renumber), `"auto"` displaces the occupant to the next free address in ITS OWN scope, `"manual"` displaces it to a caller-supplied `displace_to_address` (parsed and required only in that branch, and refused up front if it equals `to_address`). Whenever an occupant is displaced, its move is planned and executed BEFORE the source note's own move, both in the reported `moves`/`steps` and at apply time; `dry_run: false` execution runs the steps sequentially, never in parallel, and a mid-sequence failure after at least one step has already landed returns a distinguishing error naming exactly which moves completed and which one failed, rather than a bare rethrow that would hide a partially-applied vault. All three share `tools-scheme.ts`'s allowlist discipline: `ctx.notes()` is filtered through `visiblePaths` (and, per instance, `excludeRoots`) before it reaches any provider method or planning function, and the note being operated on (`path`) gets the same one-path `out_of_allowlist` check `tools-uid.ts`'s reverse lookup uses (plus an excludedRoots-territory refusal when the selected instance doesn't speak for it), refused before planning runs — a hidden note can be neither read as "what's there" nor written to by these tools. A plan's COMPUTED destinations (`MoveStep.to`, and a displaced occupant's own path) are not call arguments, so the guard's own path check never sees them — `expectedFolder` derives a folder PREFIX from the filtered notes listing, which can be shorter than a narrower allowlist entry — so every computed path is re-checked with `isVisible` before anything is planned to happen to it, unconditionally, even under `dry_run: true`. A non-dry-run success also reports `filesChanged`/`files` in its structured result (the `reportedEffects` convention `guarded.ts` and `obsidian_repoint_link` already use), so the journal's `effects` field names every file actually touched, not just the argument-derived `target`. **They cannot register through `modules-mount.ts`**: that host's `registerAll` gate refuses any tool whose `annotations.readOnlyHint !== true` (the module host's own header comment, point 1, pinned by its own test suite) — capability modules are load-bearing read-only-or-nothing by that gate's design. So these three register directly in `server.ts`, exactly the way `registerVaultWriteTools`'s `obsidian_move_notes`/`obsidian_repoint_link` already do: not a workaround, the same shape the existing hand-registered write tools use, sharing the identical `registry()`/`notes()` pair the read tools' registrar takes so both halves see the same live-reloaded settings.
  - **Six read-only scope tools** (`mcp/tools-scheme.ts`, always registered): `obsidian_schemes` (enumerate instances + capabilities + config + grammar examples), `obsidian_validate_name` (validate ONE filename against the scheme grammar — malformed address token, `name_colon`, `name_trailing_space`; a pure grammar check that reads nothing from the vault and needs no allowlist, the one-name exposure of the provider's `validateName`, NOT the whole-vault findings rule pack), `obsidian_resolve_address` (address→path(s), or path→address; duplicates are reported, never picked, same discipline as uid resolution), `obsidian_next_address` (COMPUTES only — reserves nothing; pair with `obsidian_claim_scope` for exclusivity), `obsidian_list_scope` (membersOf in address order plus up to 20 open slots with a `truncated` flag), `obsidian_expected_location` (per-note or per-address placement report). All allowlist-filtered like `tools-uid.ts`/`tools-links.ts`: `visiblePaths` runs BEFORE any provider method ever sees the notes listing, so a note occupying a slot outside the allowlist is as invisible to "what's free" as it is to "what's here" — **no existence oracle** (0 visible candidates reads as not-found even when a hidden note carries the address, matching uid resolution's precedent; an ambiguity names only visible candidates). The necessary flip side is a caveat, not a bug: under an allowlist, the "next free" address `obsidian_next_address`/`obsidian_list_scope` compute can already be occupied by a **hidden** note — allocation only computes over what the session can see, and reserves nothing regardless.

Candidate resolution runs over the allowlist-**visible** notes only (`visiblePaths`, the same set `obsidian_resolve_address` itself uses), so `address_ambiguous` can only name notes the session could have named itself, and an address whose sole claimant is hidden reads as `address_unresolved` — never `out_of_allowlist`, which would confirm the address exists (this agrees with what `obsidian_resolve_address` reports, so looking an address up and addressing by it never disagree). Resolved scheme paths fold back to their `jd:<address>` ref form in refusal text (`addressSafe`, extended alongside the uid case, one pass over both resolution lists) — belt-and-suspenders against a refusal ever naming more than the one path it blocks on.
  - **Link healing** (`mcp/tools-links.ts`) — slice 2.2, which closes Delivery step 2. The split is the point: **in band, a move heals its own links** because every move path goes through `moveWithLinks` (`mcp/move-with-links.ts`, Nelson's "B", 2026-09-29): a file-level rename (`vault.rename`, called from that module ONLY) followed by vault-mcp's own backlink rewrite and a damage check (`link_check` in the result: links still naming the old path, notes reaching the note fewer times, notes the index names but whose text has no link, notes it could not rewrite; `ok` false on any, hidden notes counted, never named). It replaced `app.fileManager.renameFile`, whose link update waits on `metadataCache.onCleanCache` — with the fleet writing constantly that wait took 1 to 25 minutes per move. Links are FOUND FROM TEXT (every note containing the old name is read; a batch shares one read through `TextCache`), so a note written moments before, with a stale index entry, is found like any other; the index is only a cross-check. Parser rules checked against Obsidian's live index: code and math hide links, `%%` comments do not, a fence counts inside a quote or a list, inline code pairs per paragraph (a list item, heading or table row starts a new one; an escaped backtick still closes a span), frontmatter opens nothing, a wikilink may hold single bracket pairs but never `[[`. The copy test also compares the parser with Obsidian's index link by link (24,749 agree, 4 only in the index, 36 only in the parser); where the index is current and counts more links than the text scan, the move reports the note in `index_only`. A move never rewrites a link inside a record (`mcp/records.ts`: the operator's record identification as the guard reads it, `record: true` by default, reaching the server through ctx's own live `recordIdentification` thunk, never `getSettings()`, which withholds it; or a record folder per the operator's `recordFolders` setting, see RECORD FOLDERS below; 01.44 rule 8); each link it leaves that no longer reaches its target is reported in `records_left` (capped at 100, `records_left_total` counts all) and is not damage. Counts are now reported (`backlinks_updated`, `backlinks_files_touched`, visible notes only), and `update_backlinks: false` renames only (the moved note's own relative links are left too). Satellites (jd-scaffold's promote, triage) still call `renameFile` themselves and keep its wait: a follow-up. **Out of band, drift is REPORTED and never repaired** (ch6: the rail detects, humans/operations fix) — `obsidian_check_links` {scope?} is read-only (no queue slot, no journal record, works in read-only mode, no `fix`/`heal` argument) and reports dangling wikilinks from Obsidian's own `metadataCache.unresolvedLinks` plus duplicated uids from the index. Both halves are **already-computed data**: it never reads a file. A third section, **`uid_coverage`** `{available, notes_total, notes_with_uid, notes_without_uid, uncovered[≤100], truncated}`, reports the identity gap over the same visible-and-in-scope set — REPORT-FIRST, no minting and no argument that could mint (that decision is a human's, pending). All three are filtered through `visiblePaths` AND the scope. **Be precise about what that buys** (Cycle 8 D2/D3): the filter is over SOURCE NOTES, so a dangling link's TEXT is reported verbatim from a visible note including path-shaped text naming somewhere outside the allowlist (it resolves to nothing, by definition, and the caller could read it out of the note) — the claim "nor the link text inside one" was false and must not be re-asserted. There is also a residual one-bit existence oracle in the other direction: a link ABSENT from the report resolved to something, possibly an out-of-allowlist note. That is inherent to letting the host resolve links; closing it would mean re-implementing resolution over a filtered vault. Both are documented in the README. A duplicate with one visible-and-in-scope carrier is not an ambiguity for that scope, matching how addressing decides. Counts are exact (a host-reported `0` stays `0` — D6), lists capped at 100 with `truncated`, duplicates sorted by uid so a report is a function of the vault. **Scope refusals are CODED** (D5), via the shared `codedError` (hoisted to `mcp/helpers.ts`, one copy with tools-locks.ts): `invalid_scope` for absolute/whitespace-padded/normalizes-out-of-the-vault, and `out_of_allowlist` for a scope naming an area the session cannot see — TYPED rather than a zeroed report, matching `scopeRefusal`'s precedent, because a zeroed report for a hidden folder is indistinguishable from a clean one. A scope that merely CONTAINS the allowlist is out of it too. Obsidian-free by construction: everything arrives through the injected `LinkSource` (structurally typed, so not even a type import from `obsidian`). `obsidian_repoint_link` remains the deliberate repair — and is **contained by the allowlist** (below).

The flag, the gate branch and their tests stay — unlike the seam's rejected `registerWriteVeto`, this is not perimeter surface that was never used; it is a documented module-host capability with six shipped users behind it. `tests/modules-mount.test.mjs` exercises the branch over a synthetic module so it cannot rot into dead code.
  - **One envelope could not cross the boundary, and it was the apiVersion-2 gap the QuickAdd pilot already logged — closed at #402 step B: a published handler may now return the SDK's `partial(data, message)` and the host turns it into `okError` with the message; the satellites' own `succeeded: false` reports can move to it as follow-ups.** The fileclass module used `okError()` — `ok()`'s shape plus `isError: true` — so a failed CLI run kept its structured per-command report. The publishing contract has no equivalent (a returned object is `ok(data)`, a throw is `fail(err)`), and throwing would destroy the report. So the satellite RETURNS the report with `succeeded: false`: a CLI failure now arrives as a successful MCP call carrying a report that says it failed. Second independent argument for the same apiVersion-2 item.
  - **Four small pieces were published into `@vault-mcp/core` rather than forked**, on the `isVisible` / `executeQuickAddChoice` / `resolveScope` precedent. `spawnEnv` and `findBinary` left `src/claude-cli.ts`, and `findObsidianBinary` left `src/mcp/tools-cli.ts` — the fileclass satellite spawns a CLI and must augment PATH and locate the obsidian binary EXACTLY as this host does, and a drifted copy fails only on some machines, silently. `scanForAcceptFence` left `src/mcp/tools-cli.ts` because its two callers are now in different plugins (this host's `obsidian_cli` template guard and the jd-scaffold satellite's template apply), and two copies of an accept predicate is how one vault gets two definitions of "accepted". That last move is behaviour-preserving BY CONSTRUCTION rather than by inspection: every symbol it is defined over was already core's, reached from here through `write-notes-compose.ts`, which is a bare re-export. All four are re-exported from their old homes, so no call site or test in this package moved.
  - **The `fileclass` D07 ruling travelled with the code.** D07 names Fileclass inspection public-optional while the implementation proxies an external CLI through `execFile`, which threat-model control #9 keeps out of the public surface. Nelson was asked with both readings stated and chose PRIVATE (2026-08-21). That ruling now applies to a whole plugin, and `kernel/operations/inventory-mcp.ts` keeps it where the rows used to be.
  - NOTE, unchanged and still easy to confuse: `obsidian_fileclass_schema` / `obsidian_fileclass_insert_fields` (`tools-integrations.ts`) are for the DIFFERENT `metadata-menu` plugin. They stayed, untouched, and are unrelated to any of this.

- **External tool registry** (`src/mcp/external-tools.ts`): other Obsidian plugins publish MCP tools via `app.plugins.plugins['vault-mcp'].api` (`apiVersion: 3` since #550 for the write declarations `protection` / `sync` / `paths`, 2 since #402 step B, read by the SDK as a floor since 1.1.0; SDK 1.2.0 leaves a declaring tool out on a host below 3, fail closed; `registerTools` — **`unregisterTools` is GONE**, removed by S2 on both sides because an owner-id address is forgeable; the disposer is the only revocation). The host fires BOTH `vault-mcp:ready` and `governor:ready` on every load, the second for the grace period. Boundary is data plus, since apiVersion 2, two crossings the design chose on purpose: INWARD, three closures per call (`CallContext`: `visible`, `isVisible`, `readOnly`) so a tool can ask "may I show this" without ever holding the allowlist; OUTWARD, the branded partial-result envelope, which the host turns into `okError` with a coded message line first. Everything else stays as it was: `inputSchema` is plain JSON Schema (zod never crosses), and a plain return is wrapped in `ok()` / a throw in `fail()`. External tools are **mutating unless `readOnlyHint: true`** (inverse of built-ins) and register through the guarded path in `buildMcpServer`, snapshot-per-connection like everything else. **A read-only claim is DISTRUSTED by default** (MEDIUM-4): believing it exempts third-party code from the queue, the journal, the allowlist, the kernel args and read-only mode all at once, on the publisher's say-so. It is believed only when the publisher's RAW plugin id is listed in the `trustedReadOnlyPlugins` setting (array, default empty, settings-tab textarea; exact match — never the sanitized form, since two ids can sanitize alike). Untrusted ⇒ registered with `readOnlyHint: false`, so read-only mode blocks it through the ordinary guard rather than a bespoke check. Read at connection-build time like the tool snapshot, so trust changes land on the next connect. The `vault-mcp-api` contract is unchanged — this is host-side policy only. Safety guards: read-only mode always applies; the path allowlist scopes recognized path-key args (path, from, to, paths, …) — mutating external tools whose args carry **no recognized path key are blocked outright when an allowlist is active** (they cannot be scoped). A v3 tool that declares `paths` (each must be a key the path walk recognizes, checked against `collectPaths` itself, and a property of its schema) is judged by those arguments: a call none of them carries a path for is refused, and every path is checked by the guard's ordinary `guardCall`. Publishers use the `vault-mcp-api` SDK — folded into this monorepo at `packages/vault-mcp-api` (published to npm as `vault-mcp-api`; the standalone repo is archived). **The npm package NAME stays `vault-mcp-api`** — it is a published contract with a real npm name, and renaming it would strand any consumer for zero user-visible gain (same reasoning as `@vault-mcp/core`). The SDK's host lookup is instead **dual-id**: it reads `app.plugins.plugins['vault-mcp']` first and falls back to `'governor'`, and waits on BOTH ready events, so one SDK build works against a host on either side of either id migration — mirroring the host firing both events. **The order flipped at S3c and the flip is load-bearing**, as is the discriminator beside it: post-split `governor` is the id of a plugin that is NOT a host (the governance provider, which exposes no `api`), so the SDK skips an id whose plugin has no `api` — a bare-presence match would resolve the provider. The same two lines are what every satellite's own host lookup uses. Its `tests/contract.test.ts` pins the SDK's shapes against this host's `external-tools.ts`, so host↔SDK drift fails a test instead of shipping.

## Build / test

- `npm run build` — esbuild, emits `main.js` (+ `bridge.mjs`). `npm test` — `pretest` builds `@vault-mcp/core`, then `tsc --noEmit && node --import tsx --test`. **The `pretest` is load-bearing, not tidiness:** since S3a the plugin's tests import several contracts (`digest`, `canonical-json`, `uuidv7`, `SessionV1`, the disposition substrate) from `@vault-mcp/core`, which resolves to `packages/core/dist` — the COMPILED output. Without the rebuild, editing `packages/core/src` and running the plugin suite tests the previous build's bytes and passes green on stale code. Do not remove it to save a few seconds.
- **The editor LSP lags** in this repo — trust `npx tsc --noEmit` (real exit code), not inline diagnostics.
- **Updating the live install** follows `docs/operator-guide.md` → "Updating a live install" (#435): the plugin folder symlinks into a versioned build directory outside every working tree, never into a checkout, and carries no `.hotreload` marker, so a build never reloads the running host by itself.
- Install for testing: `cp main.js manifest.json ~/obsidian/.obsidian/plugins/vault-mcp/` then reload the plugin (or `app.plugins.disablePlugin('vault-mcp').then(()=>app.plugins.enablePlugin('vault-mcp'))` via Advanced URI eval). The `plugins/governor/` folder is the **provider's** since S3c — copying this build there would overwrite it.

## Verifying tools live (important)

Tool handlers that call `app.*` can't be unit-tested headlessly — verify against a running Obsidian by piping JSON-RPC through `node bridge.mjs --vault <name>`.

**Async handlers (anything that `await`s, e.g. `vault.read`) require keeping stdin OPEN.** If the prober's stdin EOFs, `bridge.mjs` half-closes the socket, which aborts in-flight requests *before* their async response is sent — the tool *looks* hung but isn't. Use `( printf '<json>\n…'; sleep 4 ) | node bridge.mjs …`. A real Claude Code session keeps stdin open, so this only bites ad-hoc probes.

Pure logic (`guard.ts`, `mcp/guarded.ts`, `mcp/tools-locks.ts`, `mcp/tools-uid.ts`, `mcp/tools-links.ts`, `kernel/*` except `obsidian-probe.ts`, vault-slug, socket framing, bridge selection, discovery I/O, register-command, claude-cli `findClaudeBinary`, and `spawnEnv` through its re-export — it and `findBinary` live in `@vault-mcp/core` since the mutating tier) IS unit-tested.

**The move handlers are the one exception that IS reached headlessly.** The `obsidian` package is types-only (`"main": ""`), so a module importing `TFile` cannot load in node — `tests/obsidian-stub.mjs` registers a synchronous `node:module` resolve hook pointing the "obsidian" specifier at a stub with minimal `TFile`/`TFolder`, and `tests/link-healing.test.mjs` then `await import()`s the real handlers. It is scoped to the process that calls `installObsidianStub()`, so no other test file and no npm script changes. Use it sparingly: it exists because "a move renames link-aware" is a property of the REAL handler, not of a re-implementation. Everything else stays obsidian-free by design. The uid index's freshness is testable headlessly precisely because it is built over an injected `UidSource` — `tests/uid-index.test.mjs` drives each event type against a fake source; only the adapter (`obsidianUidSource`) and the event wiring need live verification.

## Git

Feature branch per milestone, PR to `main`, don't self-merge. Auto-review PRs you author.

**Run `./scripts/install-hooks.sh` once per clone.** It points `core.hooksPath` at `.githooks/`, enabling a `pre-commit` scan of staged content and a `commit-msg` scan of the message. Git cannot auto-install hooks, so a fresh clone is unprotected until you run it.

**NEVER paste command output into a commit message or a file without reading it first.** This is not a style rule; it is the rule that exists because it was broken. On 2026-08-27 an agent session ran a full `zsh` environment dump and pasted it into a COMMIT MESSAGE — 249 lines, 96 `NAME=value` pairs — and pushed it to this public repo. Six live credentials went out: two API keys, a GitHub OAuth token with `repo` + `workflow` scope, and three service tokens. GitHub's scanner caught it in seconds and two vendors auto-revoked; the GitHub token was still live fifteen hours later.

Three things about that are worth carrying:

- **It was in the message, not a file.** No file, tree, or branch in this repo has ever contained that text. A `.gitignore` rule could not have helped, and a hook that only scans `git diff --cached` — the obvious design, and the first thing built here — sails straight past it. That is why there are two hooks.
- **It is unfixable after the fact.** The commit reached `main` through a squash-merge, so it is in the permanent history of a public repo. Deleting a branch does nothing. Rotation is the only real remedy, which is why the hooks refuse rather than warn.
- **Half the secrets had no vendor prefix.** `NGROK_AUTHTOKEN`, `SEMGREP_APP_TOKEN` and a gateway token are invisible to GitHub's scanner — nothing recognizes their shape. `scripts/secret-scan.mjs` catches them by the NAME they are bound to, and refuses any block of 20+ `NAME=value` lines outright regardless of content, because the next dump will contain a token format nobody has a rule for.

Redact before you paste; better, do not paste environment output at all. If you need to show a variable exists, show the name.
