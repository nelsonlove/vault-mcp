# Vault Provenance (plugin id `vaultmcp-provenance`) — architecture & working notes for Claude Code

Derived-content provenance as its own Obsidian plugin: is a generated note still true to the sources it declares, which installed plugins have no note, and regenerate the plugin-audit note without destroying what a human wrote in it — published to the Governor host through `vault-mcp-api`. Ported from the standalone `obsidian-provenance` Python CLI, folded into the host as its `provenance` capability module, and extracted here in the suite split's mutating tier, following `packages/quickadd-choices-compile` (the pilot), `packages/skills` (S4), `packages/triage` (S5), `packages/crosssession` (S6) and the S7 read tier (`packages/health`, `packages/vocab`, `packages/bases`). Package layout, build/test commands, and the extraction's four consequences are in `README.md`; the user-facing model is `docs/provenance.md` at the repo root.

## Locked decisions (don't relitigate without reason)

- **THE `path` → `note_path` RENAME (see the next bullets) COSTS MORE THAN ALLOWLIST AVAILABILITY, and the ledger has to be complete — do not describe that trade without this half.** The host's `collectPaths` is not the allowlist's private walker: the SAME list feeds record immutability (a mutating op that NAMES a note carrying `record: true` is refused at dequeue), the advisory-lock consult (a foreign scope claim covering a named path is disclosed on the call), and the journal record's argument-derived `target.path`. With no argument in the host's `PATH_KEYS`, all three see an EMPTY path list on every call this plugin makes. So a `record: true` note is no longer protected from this plugin's writes by that kernel check; a foreign claim covering the note is no longer disclosed; and the journal record names no target path — mitigated only where the handler returns `filesChanged` / `files`, which the kernel records as `effects`. **None of those three is gated on an allowlist**, so they are lost in the ordinary, no-allowlist case as well — the opposite direction from the allowlist tightening, and it must never be folded into it as if the change were strictly stricter. The record guard's documented posture is already fail-OPEN and "protective, not load-bearing", so this widens a gap that was open by design rather than closing one; it is still a real reduction, and it is the strongest argument anyone will have for reversing the rename. The reversal is one word per tool. **[ACTED ON, in two rounds, and this package ended where it started — deliberately. Round 1 (2026-09-07): the host added `note_path` to its path-key list, restoring all three checks for every argument-named note. Round 2 (2026-09-07), after review: that fix reached further than its reason. The three checks it restores all bind at the MUTATING dequeue, so they buy a READ nothing — and `check` is a read whose answer enumerates paths the caller cannot see. So `check`'s argument is now `note`, this package carries NO host path key again, and the fail-closed posture below is the one that ships. The mutating tools elsewhere in the tier (`vaultmcp_fileclass_set`, `vaultmcp_jd_scaffold_promote_to_folder`, `_reindex_category`) keep `note_path` for exactly the reason this paragraph gives. Do not delete this paragraph: it is the argument that made round 1 correct, and the rule "path-key iff it mutates the note it names" is derived from it.]**

- **THE PUBLISHED TOOL NAMES CHANGED, AND SO DID ONE ARGUMENT NAME — know this before touching anything here.**

  | shipped (module)       | bare name here | published (satellite)        |
  |------------------------|----------------|------------------------------|
  | `provenance_check`     | `check`        | `vaultmcp_provenance_check`     |
  | `provenance_reconcile` | `reconcile`    | `vaultmcp_provenance_reconcile` |
  | `provenance_regen`     | `regen`        | `vaultmcp_provenance_regen`     |

  Two compositions: the host publishes an external tool as `<sanitized publisher id>_<bare name>`, so **the plugin id IS the tool namespace** (`vaultmcp-provenance` → `vaultmcp_provenance`); and the BARE names shed their `provenance_` prefix, because keeping them would have published `vaultmcp_provenance_provenance_check`. Same trade the bases satellite made with `base_`. **Beside those, `check`'s note argument has been spelled three ways** — the allowlist bullet below is why, and it is the load-bearing half of this extraction:

  | tool | at the fold | extraction (S8) | now (round 2, 2026-09-07) | why |
  |---|---|---|---|---|
  | `check` | `path` | `note_path` | **`note`** | a READ whose answer enumerates every path the note's `derived-from` globs resolve to ⇒ not a host key ⇒ F3 refuses it outright under an allowlist |
  | `reconcile` | — | — | — | takes no arguments; pathless from the start |
  | `regen` | `write` | `write` | `write` | a boolean; the audit's destination is configuration, named by no argument |

  Round 1 briefly put `check` on `note_path` while `note_path` was a host key, which made it per-path scopable — the exact posture the bullet below rejects. Round 2 spells it `note`, which is not a key, and the tier's MUTATING tools keep `note_path` instead.

  The cost is real and should not be understated: **it breaks any agent session or saved prompt calling the old names, or passing `path` to the freshness check**, and the host's own locked decision says renaming shipped tool names breaks agent sessions for zero semantic gain. What buys it is that the stuttering alternative is worse to read and to type, and that one rename motion is cheaper than two. **Reversing the tool names is a one-line change** — `manifest.json`'s `id`, plus the strings in `tests/host-shim.mjs` and the settings tab's status line; nothing else encodes the prefix (the specs carry BARE names, the prefix is the host's). **Reversing the argument is one word** — `note` → `path` in `src/tools.ts` (and `note_path` is the third spelling, reserved for MUTATING tools; see the table above). Both pinned by the `publication` tests.

- **THE ALLOWLIST POSTURE IS FAIL-CLOSED ON THE WHOLE SURFACE, and taking `check`'s argument out of the host's path-key list is what makes it uniform.** The host's F3 gate (`packages/host/src/mcp/external-tools.ts`, the block commented F3) is evaluated **at call time on the ACTUAL ARGUMENTS**: `if (settings.allowlist.length > 0 && collectPaths(args ?? {}).length === 0) return fail(...)`. `reconcile` takes no arguments and `regen` takes only a boolean, so both were pathless already; renaming `check`'s argument out of `PATH_KEYS` — `path` → `note_path` at the extraction, then `note_path` → `note` at round 2, when `note_path` itself became a key — makes the third match, and all three are then blocked WHOLESALE under an active allowlist. The alternative — leaving `check` scopable — was rejected on three grounds, in order of weight:
  1. **A satellite cannot see the host's allowlist.** `ctx.getSettings` is a dormant seam and nothing supplies it, so this plugin cannot filter anything itself.
  2. **Host-scoping `check` would check the wrong thing.** The host would scope the ONE note the call names, and the answer would still enumerate every path the note's `derived-from:` globs resolve to — files the session cannot see, named back to it. **The host scopes the note you NAME, not the paths the answer CONTAINS.** That is precisely the bases review's "do not write 'the host scopes it' and stop there", and here it is avoidable rather than merely disclosable.
  3. **One-tool-open, two-tools-shut is a posture nobody can state in a sentence** — and the open one is the one that leaks.
  **The cost must be stated wherever the posture is:** under an active allowlist provenance is UNAVAILABLE, not partially available. With NO allowlist configured — the ordinary case — nothing changes at all. Stated in the README, the settings tab and `src/tools.ts`. Pinned by `publication: … NOT ONE argument is a host path key`, with a vacuity guard asserting that `path` AND `note_path` ARE on the host's list while `note` is not — so "no keys" is a real finding rather than an empty snapshot.

- **`tests/host-shim.mjs`'s `HOST_PATH_KEYS` is a REVIEW AID, never a live tripwire.** It is a snapshot copy of the host's `PATH_KEYS` + `ARRAY_PATH_KEYS`, carried as DATA so this package can assert which of its own argument names are on the list. It does not read the host's source and it will NOT fail when the host changes its list — it only makes such a change show up as a diff a reviewer must reconcile against the fail-closed posture. **The pin that actually fires lives in the host's own `tests/guard.test.mjs`, over the live `collectPaths`.** Do not claim otherwise in a comment, a doc or a report.

- **Issue #381: this takes the SECOND of three, and one remains. The issue is NOT closed.** #381 asked whether the host's whole-vault read exception had grown by precedent rather than by decision, and named three tools that scan the entire vault with no allowlist filtering: `obsidian_health`, `provenance_reconcile`, `obsidian_conformance_debt`. At S7 the health extraction took `obsidian_health` out of the host — as an untrusted external tool with no recognized path key it is now blocked WHOLESALE under an allowlist, which is stricter than the documented-exception outcome the issue was weighing. That left two. **This extraction takes `provenance_reconcile` out on the same terms, leaving `obsidian_conformance_debt` alone — and that remaining one is still owed the enumerate-or-filter decision.** [Update 2026-10-14: `obsidian_conformance_debt` has left the host too, as the `vaultmcp-conformance` satellite's `vaultmcp_conformance_debt`, refused outright under an allowlist on the same terms; no tool on #381's list remains in the host. See `packages/conformance/CLAUDE.md`.] Be precise about what changed and what did not: **the reconcile scan still reads the whole vault** (every `.obsidian/plugins/*/manifest.json`, `.obsidian/community-plugins.json`, and every note under the configured notes root, unfiltered), deliberately, because a partial audit is a misleading one — an unscanned slot reads exactly like a plugin nobody ever noted. **What changed is the outcome under an allowlist: refused outright instead of quietly returning a whole-vault answer.** Do not write that #381 is resolved, and do not write that the scan was narrowed.

- **`ctx.getSettings` is a DORMANT seam, kept deliberately, and it was dormant BEFORE the extraction too.** The module's `ProvenanceToolsCtx.getSettings` carried a comment saying it was "retained for a future cycle that scopes the audit read surface to the allowlist" and it was never applied — the audit runs over the whole notes-dir by design. Carry that honestly: it is not a filter that this extraction switched off. Do not delete it (an apiVersion-2 `vault-mcp-api` that can carry the caller's scope to a publisher makes it live with no code change), and do not describe it as protection. There is no `ctx.visible` here because the module never had one. The test that supplies `getSettings` asserts the honest thing — that supplying it changes NOTHING today.

- **Config is read PER CALL, never captured — and that IS a change, not a carry-over.** The module ran `const cfg = provenanceConfigOf(ctx.config)` ONCE at the top of `registerProvenanceTools`. That was survivable inside the host, which rebuilt the specs per connection; as a satellite it would mean a settings edit never landing until an Obsidian reload. `ProvenanceToolsCtx.config` is a THUNK now, resolved inside each handler. Pinned by the "config is read PER CALL" test.

  `main.ts` also **disposes and re-publishes on every settings write**, the triage / cross-session / bases pattern. Be honest about what that buys HERE: unlike `vaultmcp_bases_query` (or `vaultmcp_crosssession_channels`, before that satellite was retired on 2026-10-15), **none of this package's descriptions currently interpolates a config value**, so today the republish is defence rather than a fix — the host snapshots a published spec's description and schema when it registers it, so the day someone renders `notesDir` into a description (a reasonable thing to want) a missing republish would misreport it to every agent reading the tool list until a reload. Do not "simplify" `republish()` back into a single `this.register(publishTools(...))` in onload on the grounds that nothing needs it yet.

- **ONE adoption, not two, and the absence of a second was CHECKED.** Config adopts once from the host's `modules.provenance.config` under the three rules (never write the host's settings; run once; own values win). Cross-session needed a SECOND, separately-latched adoption because it had live operational state outside `data.json`. **This surface has none**, verified rather than assumed: the pure core touches nothing but the four injected vault primitives (`noteFrontmatter` / `read` / `stat` / `glob`); the only write in the package is `writeNote`, which writes ONE vault note — the audit — that stays exactly where it is across the extraction; and nothing in the module's source ever referenced `manifest.dir`, an install id, the journal directory or any state `*.json`. The audit's own freshness witness lives in that note's frontmatter, in the vault. Recorded so the absence is a finding rather than an oversight, and pinned by a test over `DEFAULT_PLUGIN_SETTINGS`' key set.

- **`hostSettings === undefined` means HOST NOT READY, never "host with empty settings".** The host declares `settings` without an initializer and assigns it mid-`onload`, so an instance visible in `app.plugins.plugins` before that assignment must not burn the one-shot latch. The check in `main.ts` is `host.settings !== undefined`, not a truthiness test. Found by the skills extraction's review; do not "tidy" it into `if (host?.settings)`.

- **EVERY FAILURE PATH HOLDS THE LATCH OPEN, and it is implemented rather than promised.** The cross-session review (2026-09-05) caught a satellite that swallowed a `saveData` failure, burned the latch and logged success — permanently losing what it claimed to have adopted. Here the persistence is INJECTED (`runConfigAdoption(current, hostSettings, save)` in `settings.ts`) so the discipline is headlessly provable: the adopted object replaces the current one only after `save` RESOLVES, so a throwing write leaves `adoptedFromHost` false in memory and on disk and the next load retries. Pinned by "a THROWING save leaves the latch open", including the successful retry.

- **Two write guards, both BEFORE the write, and neither is optional.** `guardAuditDestination` refuses to regenerate over a note this generator did not stamp — the reachable data-loss case is `notesSource: "flat"` with the shipped JD notes root, which derives onto `00-09 System/07 Repositories/07 Repositories.md`, the area's own folder note; it has no `human:start` markers so a regen would replace its whole body, and the accept-guard does not fire because it carries no acceptance field. `guardProvenanceWrite` runs the shared `acceptTransitionReason` over the frontmatter the regen WOULD land, so a rendered audit can never introduce or change an accepted-family assertion. The rendered frontmatter carries only DERIVATION fields, so a clean regen always passes — running the guard is the load-bearing invariant, not a filter the tool expects to trip. **Derivation is not acceptance**, and no tool here carries an accept/approve verb.

- **Handlers return plain data and THROW on refusal**, with the host's `fail()` rendering a lowercase-snake `code` as `Error [code]: message`. There is no `ok`/`fail`/`codedError` import here — those helpers are host-internal. Which envelopes are byte-compatible with the folded era and which are new, checked rather than assumed:
  - `AcceptForbiddenError` carries `code = "accept_forbidden"` (`packages/core/src/accept-guard.ts`) ⇒ `Error [accept_forbidden]: …`. **Unchanged.**
  - `AuditDestinationError` carries NO code ⇒ `Error: refusing to regenerate over …`. **Unchanged, deliberately.** Giving it a code would be one line and a real envelope change for a live refusal; it was left alone so no refusal an agent parses shifts shape at the extraction. Pinned by test, including `e.code === undefined`.
  - A kernel throw (`<path> has no derived-from`, an unparseable `generated`) ⇒ `Error: …`, uncoded. **Unchanged** — the module's `fail(e)` produced exactly this, and the satellite reproduces it by letting the error propagate rather than catching it.
  - **NEW: `invalid_argument` and `invalid_path`**, both on `check`'s note argument (`note` since round 2). Neither could fire in the folded era, where zod's `.min(1)` ran inside the host's own registration; across the publishing boundary the bound does not survive, so the check moved into the handler and needed a name.

- **`regen`'s SUCCESS envelope gained two keys, and that is a deliberate addition rather than a carry-over.** A successful write now returns `filesChanged: 1` and `files: [<audit note>]` beside the unchanged `written`. The audit's destination is CONFIGURATION and is named by no argument, so the host's argument-derived journal `target` is empty for this tool — `reportedEffects` (the `guarded.ts` convention) is the only way the file actually written reaches the record's `effects` field. It survives the boundary because the host wraps a returned object as `ok(data)`, making this the `structuredContent` the kernel reads. A dry run reports no effects, because "would change" is not "changed". If you remove those two keys you silently empty the journal record for the one tool whose write target is never in its arguments.

- **`note`'s bound is re-applied in the handler, and a BACKSLASH is refused outright before every other check.** The SDK converts zod to JSON Schema and the host converts it back through a small subset (`packages/host/src/mcp/json-schema-to-zod.ts`): `type`, `description` and string `enum` survive; `default`, `min`, `max`, `pattern` do NOT. So `.min(1)` runs again in `requireNotePath` — the `vaultmcp_skills_release` semver bug, avoided rather than repeated. The backslash rule is the one the triage and bases satellites adopted: every check downstream splits on `/` alone, so `Meta\..\..\secret.md` reads as ONE opaque segment here and as a traversal to whatever normalizes it later, and an Obsidian path never legitimately contains one. Refusing closes the class rather than the instance.

- **The kernel came over VERBATIM, and the ONE-definition rules inside it still bind.** `globSegmentRe` is the single glob-segment matcher, used by both `globMatchesPath` (the witness's structural test) and the adapter's expander — they were two copies once, and the weaker one threw `Unterminated character class` on an unbalanced `[` in a configured folder name. `notesGlob` is the single definition of what a layout enumerates, called by both `reconcile` (what the audit reads) and `auditDerivedFrom` (what it declares it read). `resolveEntries` is the single resolution used by both the witness stamp and the freshness check, so the count and the check are the same arithmetic by construction. Do not re-derive any of the three at a call site.

- **Obsidian-free by construction** everywhere except `src/obsidian-source.ts` and `src/settings-tab.ts`. The glob walker lives in the adapter (it is the one thing that needs a real vault listing) and imports its segment matcher from the kernel.

## Build / test

- `npm run build` — esbuild, emits `main.js`. No assets, no defines: like the triage, cross-session and bases satellites and unlike skills, there is nothing to embed.
- `npm test` — `pretest` builds `@vault-mcp/core`, then `tsc --noEmit && node --import tsx --test`. **The `pretest` is load-bearing, not tidiness:** the tests reach the accept-guard (`AcceptForbiddenError`, and through `src/tools.ts` also `acceptTransitionReason` / `parseGuardFrontmatter`) through `packages/core/dist` — the COMPILED output. Without the rebuild you test the previous build's bytes. 101 tests.
- Install for testing: copy `main.js` + `manifest.json` into `<vault>/.obsidian/plugins/vaultmcp-provenance/` and reload the plugin. During development add an empty `.hotreload` file in that directory so the hot-reload plugin picks up rebuilds — it belongs to the vault install, not to this repo.

## Headless testing

Everything except `src/obsidian-source.ts` and `src/settings-tab.ts` is unit-tested without Obsidian: the freshness engine, the entry resolution, the reconcile in both notes layouts, the renderer and the regen are pure over a fake `ProvenanceBackend`; both write guards run over plain records and plain text; the adoption runs over plain records with an injected `save`. `tests/host-shim.mjs` reproduces the three things the host does to a published tool — the `<sanitized id>_<bare name>` naming, the `ok()`/`fail()` envelopes including the coded rendering, and the annotations it derives from an UNTRUSTED `readOnly` claim — so the handler tests assert the envelopes an agent actually sees rather than raw return values.

It deliberately does NOT reproduce the F3 pathless-tool block, the path allowlist, the write queue, the journal, read-only mode or the record-immutability guard. Those are host code with host tests, and a second copy could drift into asserting a posture the host does not enforce. The module's suite asserted several of them by mounting through the host's `modules-mount.ts` against a `fakeServer` (a `collect()` helper rendered its config tab, and `forbiddenToolName` checked the accept-verb tripwire); that was possible only because it lived in the host's tree, and those assertions belong where the code is. What replaced them is the `publication` block: the wire names, the shed prefix, the untrusted read-only claim, the no-path-key pin, the re-applied schema bound, the backslash refusal and the coded/uncoded rendering of each refusal class.

`src/obsidian-source.ts` is NOT reached headlessly. Its un-headless surfaces are the duck-typed `vault.adapter` reads, the segment-by-segment glob walk over `adapter.list`, and the create-or-modify write (including the parent-folder creation). Verify them live against a running Obsidian — the glob walker in particular, because every count the audit stamps depends on it enumerating the same set the freshness check will later resolve.
