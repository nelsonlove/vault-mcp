# Governor (governance provider) — Authoritative Tool Inventory

(Plugin id `governor`. Since the S3c split this id names the GOVERNANCE PROVIDER only; the MCP host is a separate plugin, id `vault-mcp`, and its own surface is inventoried at `packages/host/TOOL-INVENTORY.md`. The provider registers no MCP server of its own — it PUBLISHES the five tools below into the host through `vault-mcp-api`, exactly the way any third-party plugin publishes, and they appear on the wire only while the host is installed, enabled, and loaded.)

Source of record for every tool this plugin publishes. Generated by reading `packages/governor/src/tools/*.ts`.

**Count summary:** **5 published tools** — 3 read-only, 2 mutating. There are no conditional tools, no module-mounted tools and no alternative surface here; the provider's other capabilities (the review pane, the gesture perimeter, admission, cohorts, promotion, the standing chain) are deliberately NOT MCP tools, and the pane publishes no accept or admit verb in any API. Whether these five appear at all is a function of the host: a connection sees them iff the provider is loaded when the host builds that connection's server, since the host snapshots its external-tool registry per connection.

## Four names did not change, one was renamed, and the carve-out is closed

The publishing rule is `<sanitized owner id>_<bare name>`. Under it alone these five would have been published as `governor_governance_pending_review`, `governor_governance_revisions`, `governor_governance_submit_revision`, `governor_governance_mandate_draft` and `governor_governance_mandates`.

So the host carries `GRANDFATHERED_TOOL_NAMES`: a checked-in map from each of the five spellings to the SINGLE owner id (`governor`) permitted to publish it BARE. Two things about its shape are load-bearing. It is host-held rather than a flag on the published spec, because an `exactName: true` flag would be publisher-controlled and any plugin could then claim any name. And it names the OWNER as well as the name, rather than trusting whoever holds a seam registration — gating on "is a registered governance provider" would let any plugin that registers a write observer claim a locked spelling, which is strictly worse than gating on one hard-coded id.

**IT CARVES OUT THE PREFIXING RULE AND NOTHING ELSE.** The host separately REFUSES any published name beginning `obsidian_` (the F1 check in `packages/host/src/mcp/external-tools.ts`), and that refusal is UNCONDITIONAL — a grandfathered name is checked like any other, and no entry in the table may begin `obsidian_`. This is why the fifth tool is called `governance_pending_review` and not what it used to be called.

**`obsidian_pending_review` → `governance_pending_review`, Nelson's ruling of 2026-09-08.** The table's first draft held the old spelling, which would have made it an F1 exception as well. Three reasons it was refused, and they bind the next case: **(1)** an F1 exception, even one gated on a provider id, permanently weakens a namespace-integrity rule and becomes the precedent for the next exception — the rule is worth more than one name's continuity; **(2)** the locked decision forbids renaming shipped names *for zero semantic gain*, and this rename HAS gain, because the `obsidian_` prefix branded a governance tool as a host built-in, which after the split is an architectural lie, while the new spelling says what the tool is and matches its siblings; **(3)** the breakage is near zero — MCP tools are discovered per session, and the one glob in this repository that patterns on the old spelling (`packages/host/cc-plugin/hooks/scripts/block-record-writes.sh`'s `*pending_review*`) still matches.

That name is nevertheless IN the table, and the reason is not continuity: it is family consistency. Four bare `governance_*` names beside one `governor_governance_pending_review` would recreate, in the tool list an agent actually reads, exactly the incoherence the rename removes.

**The table is CLOSED.** Nothing is added to it. Every other satellite in the suite paid the rename tax at its own extraction, deliberately — the plugin id IS the tool namespace, and the seven `obsidian_jd_*` renames were recorded as a boundary rather than a choice for the same reason. The four that did not pay it could not, because they were already on the wire when the split happened and renaming a shipped tool name breaks every agent session for zero semantic gain; the fifth paid it after all. A new tool in this package takes the ordinary namespaced form.

## Allowlist posture under the host's gate

Publishing moved the enforcement boundary from inside these tools to the host, and it got STRICTER in the move — the same finding class as S4, S5, S6, S7 and the mutating tier.

**Read-only claims are distrusted.** An external tool's `readOnlyHint: true` is believed only when the publisher's raw plugin id is listed in the host's `trustedReadOnlyPlugins` setting. Untrusted, the host registers the tool with `readOnlyHint: false`, so read-only mode blocks it through the ordinary guard rather than a bespoke check. Listing `governor` there is what restores read-only treatment to the three read tools; it is an operator decision and the default list is empty.

**Under an ACTIVE path allowlist, F3 blocks any external tool whose arguments carry no recognized path key,** because such a tool cannot be scoped. Only one of these five carries one:

| Tool name | Path-key argument | Under an active path allowlist |
|---|---|---|
| `governance_pending_review` | none (no arguments at all) | refused wholesale |
| `governance_revisions` | none (`folder` is not a path key) | refused wholesale |
| `governance_submit_revision` | `path` | proceeds, scoped per-path |
| `governance_mandate_draft` | none (`scope_include` / `scope_exclude` are not path keys) | refused wholesale |
| `governance_mandates` | none (no arguments at all) | refused wholesale |

**They also lost their in-tool visibility filtering, and that is a real reduction, not a tidier design.** As host-registered tools, `governance_pending_review` filtered its entries, `governance_revisions` filtered its listing, and the mandate tools hid out-of-scope drafts, each by reading the host's guard settings directly. A published satellite cannot reach those settings — the publishing contract carries no caller scope, which is the standing apiVersion-2 gap — so those filters are dormant. What replaces them is the host's own gate, which refuses the whole call instead of trimming the answer. The net effect under an allowlist is stricter (four surfaces unavailable rather than partially available); with no allowlist configured, which is this operator's case, the filters were vacuous anyway and nothing changes.

The reversal, if it is ever wanted, is one word per tool: spelling an argument `path` would make that surface per-path scopable. It is not wanted for the four reads — scoping the argument while the answer's blast radius exceeds it is the illusion of a check, the reasoning that kept cross-session's `channel` un-path-keyed and sent the fileclass and provenance reads pathless.

## Not tools, deliberately

Acceptance, admission, cohort selection, mandate ACTIVATION, revocation, promotion and standing advancement are human gestures in the review pane. None of them is published here, and the seam the host offers has no hook class that could carry them: a registrant may observe a write or add a refusal, and nothing else. `governance_mandate_draft` is the boundary case that proves the rule — an agent may author a delegation request, and only a human gesture turns one into authority.
