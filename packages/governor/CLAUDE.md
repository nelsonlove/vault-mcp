# Governor (plugin id `governor`) — the governance provider — architecture & working notes for Claude Code

Everything in the suite that decides authority: proposals, verification, admission, cohorts, mandates, transformations and promotion, the Git-backed history store, the legacy acceptance machinery with its cutover and store binding, and the human-only review pane. It is an Obsidian plugin that plugs into the **Vault MCP host** (`packages/host`, plugin id `vault-mcp`) through the governance seam, and publishes five MCP tools through `vault-mcp-api` like any other publisher.

Extracted from the host at S3c of the suite split (`docs/suite-split-design.md` §2, §5, §6), the last and largest of the extractions and the only one where the extracted half kept the plugin id. The migration map is `docs/s3c-migration-plan.md`.

## Locked decisions (don't relitigate without reason)

- **THIS PLUGIN KEPT THE ID `governor`, AND THAT IS WHY ALMOST NO STATE MOVED.** `.obsidian/plugins/governor/governance/` — baselines, the acceptance log, the pending index, proposals, mandates, sessions, the cutover marker, the store binding — and `~/.claude/governor/history/<vault-slug>/`, the standing chain's git directory, are the operator's live authority evidence. The safest migration for them was none, so the HOST took the id `vault-mcp` back instead and copies its journal, its install id and its own settings keys out of this folder once, without moving or deleting anything. The host's adoption surface (`AdoptionFs`) has no `rename` and no `remove`, so that is a property of the interface rather than a rule someone has to remember.

- **`data.json` IS SHARED, AND THIS PLUGIN MERGES ON SAVE — NEVER REPLACES.** The file in this folder is the pre-split plugin's, and it still holds every HOST setting: the allowlist, read-only mode, the schemes, the CLI policy, the protected-property rows. Two failure modes make the merge load-bearing rather than tidy. **Ordering:** Obsidian gives no guarantee about which plugin loads first, and a save containing only this plugin's keys before the host had adopted would delete the host's allowlist and read-only mode — whose fallback is `DEFAULT_SETTINGS`, i.e. socket enabled, read-only OFF, allowlist EMPTY. The guard config would silently reset to open. **Rollback:** the documented rollback is to reinstall the single-plugin build under this id, and it reads this same file. Every key it ever wrote has to still be there. The split of which key belongs to whom is declared ONCE, in `@vault-mcp/core`'s `splitSettings` — a key both plugins claim gets each save overwriting the other's edit, and a key neither claims is dropped.

- **THE PUBLISHED TOOL NAMES: four kept, one RENAMED.** The five tools publish as `governance_pending_review`, `governance_revisions`, `governance_submit_revision`, `governance_mandate_draft`, `governance_mandates` — all BARE, where an external tool ordinarily publishes as `<sanitized owner id>_<bare name>`. The host's closed `GRANDFATHERED_TOOL_NAMES` table is what allows it, and it carves out the PREFIXING rule and nothing else.
  - **`obsidian_pending_review` → `governance_pending_review` (Nelson's ruling, 2026-09-08).** The first draft grandfathered the old spelling, which would have made the table an exception to **F1** — the host's refusal of any published name beginning `obsidian_`. Nelson ruled against it: **(1)** an F1 exception, even one gated on a provider id, permanently weakens a namespace-integrity rule and becomes the precedent for the next exception; **(2)** the locked decision forbids renaming shipped names *for zero semantic gain*, and this rename HAS gain — the `obsidian_` prefix branded a governance tool as a host built-in, which after the split is an architectural lie, while the new spelling says what the tool is and matches its siblings; **(3)** the breakage is near zero, because MCP tools are discovered per session and the one glob patterning on the old name still matches. **The tool is OFF the do-not-rename list. `governance_revisions` and `governance_submit_revision` remain on it.**
  - The renamed tool is nevertheless IN the table, because the family has to be spelled consistently: four bare `governance_*` names beside one `governor_governance_pending_review` would recreate, in the tool list an agent actually reads, exactly the incoherence the rename removes.

- **THE PUBLISHING BOUNDARY MADE FOUR OF THE FIVE STRICTER, AND ONE WEAKER. Both halves are real.** Stricter, and it is the same finding every satellite extraction since S4 has recorded: the host DISTRUSTS an external `readOnlyHint: true` unless the operator lists `governor` in `trustedReadOnlyPlugins`, and under an active path allowlist the F3 gate blocks any external tool carrying no recognized path key — so four of the five are refused wholesale while an allowlist is active, and only `governance_submit_revision` (which takes `path`) stays scoped per-path. They also lose their in-tool `isVisible` filtering, because a satellite cannot reach the host's guard settings; the `getSettings` seams are kept DORMANT (the skills / triage / cross-session precedent) so an apiVersion-2 SDK carrying caller scope wakes them with no code change. **Weaker, and named as a regression rather than folded into the trade:** `governance_mandate_draft` can no longer default `delegate` to the calling connection's session, because a published tool does not learn which connection is calling. It refuses `no_session` instead. The proper close is the same apiVersion-2 item.

- **THE SEAM CARRIES TWO HOOKS AND THIS PLUGIN REGISTERS BOTH — nothing else crosses.** `registerWriteObserver` takes the exact bytes of a completed write and this plugin turns them into a proposal (candidates flow outward; a proposal confers nothing). `registerSessionRefusal` answers refuse-or-not at dequeue, and before the host rotates an expired session (purpose `"rotate"`, #568: there a store read error refuses) (refusals flow inward; a refusal can only make the host refuse MORE, and `null` is silence, not an allow — the type cannot express permission). Registration goes through `vault-mcp-api`'s `registerGovernance`, which handles load order, host reload and cleanup exactly as `publishTools` does. The disposer is the only revocation.

- **THE SESSION SPLIT (condition 7), and what it cost.** Condition 7 ruled the host mints and keeps the lifecycle record, and that **the seam carries no connection-lifecycle notification** because the provider never mints. S3c builds exactly that and adds no seam surface: the host writes `opened`/`closed`/`expired` into its OWN `sessions.jsonl` and this plugin never hears about them. What this plugin still owns is REFUSAL and the mandate binding, and both are facts about a session ID rather than about a session RECORD, so they fold by id (`foldSessionAuthority`). `foldSessionEvents` is untouched and every historical line in `governance/sessions.jsonl` still folds exactly as before. **The cost:** `revoke` and `attachMandate` no longer verify that the session is open. Revocation is safe by construction — it can only ADD a refusal. Mandate attachment is safe on this plugin's own prior ruling that fit binds by session id and the record "is provenance, not a gate" (`wiring/mandate-wiring.ts`). What is genuinely lost is the refusal of a mandate attach to an already-expired session, which surfaced as a `sessionAttachWarning` and never undid the grant. **Flagged for ratification**, because condition 7's sentence was written without `attachMandate` in view.

- **#261's DRIVE MOVED TO THE WRITE OBSERVER, AND IT IS NARROWER.** Chromium suspends renderer timers while the Obsidian window is occluded, so the review queue's 2.5s poll does not tick during unattended sessions — exactly when agents write. Before the split the host nudged the queue from inside its `journal.append` wrapper: every append, whatever it was. The journal is the host's now and no journal-growth hook was added to the seam, so `main.ts` nudges from the seam's **write observer** instead, which the host dispatches immediately after its own journal append. That covers what the queue is for — proposals come from write facts — but it does NOT cover appends that produced no write facts (idempotent replays, deduped waiters, key mismatches, mutating operations that are not native note-writes). Those wait for the interval. Closing it properly means a journal-growth fact on the seam, which is a design conversation, not a patch.

- **THE ACCEPT PERIMETER IS UNCHANGED, AND THE SPLIT DID NOT STRENGTHEN IT.** Every accept-capable capability is still module-scope in `wiring/wiring.ts` and `wiring/pane.ts`, held in module-private WeakMaps, reached only through gesture-gated pane buttons wired with `addEventListener` and gated on `isRealGesture`. `tests/governance-module.test.mjs` is the source tripwire, and it is load-bearing. **Say this correctly:** the boundary is held by the WeakMaps and the absence of accept exports, NOT by the fact that the settings tab now sits in a different file or that the host is now a different plugin. `settings-tab.ts` hands `renderGovernanceSettings` a container and holds no accept-capable value; that was true before the split for a stronger reason and is true after it for the original one.

- **THE REVIEW QUEUE IS DERIVED FROM THE HOST'S JOURNAL.** `wireGovernance` takes `journalDir` as a REQUIRED dep, resolved in `main.ts` from the host plugin's own `manifest.dir`. With no host loaded there is nothing to derive from, so the pane REFUSES TO MOUNT and says why, with a sticky Notice. A pane showing a permanently empty queue while saying nothing about it is the silent-zero class this repo has paid for twice.

- **What was published into `@vault-mcp/core` so this plugin could stop importing the host**, each because a second copy would be a correctness bug: `splitSettings` (above), `CHANGE_CLASSES` (its canonical ORDER is what two producers hash a proposal subject over — a drifted copy forks the standing chain), `NOTE_WRITE_ACTION` (the id, version and declared classes the write observer speaks for — two copies let the host bump the version while this plugin quietly stopped proposing), and `vaultSlug` (the host names the socket by it and this plugin names the standing chain's git directory by it — a one-character disagreement reads as "chain absent here" on the machine holding the chain).

- **ONE RELATIVE IMPORT STILL ESCAPES THIS PACKAGE, deliberately and only at test time.** `src/kernel/operations/inventory-authority.ts` type-imports the action-registry vocabulary from the host. It is a declaration nothing at runtime reads, its own header argues the case, and `tests/governance-module.test.mjs` pins BOTH halves — that it is the only escape, and that nothing else under `src/` imports it, which is what makes "costs the built plugin nothing" true rather than aspirational.

## Build / test

- `npm run build` — esbuild, emits `main.js`. **No bridge and no defines: the bridge is the HOST's**, embedded in its `main.js` and written to `~/.claude/vault-mcp/` on load. A second copy shipped from here would be a second writer of one file, which is the class of drift the split exists to remove.
- `npm test` — `pretest` builds `@vault-mcp/core`, then `tsc --noEmit && node --import tsx --test`. The `pretest` is load-bearing: the tests reach `isVisible`, `SessionV1`, `splitSettings` and the action contract through `packages/core/dist`, the COMPILED output. Without the rebuild you test the previous build's bytes.
- Install for testing: copy `main.js` + `manifest.json` into `<vault>/.obsidian/plugins/governor/` and reload. **Enable the host FIRST** — see the migration plan's live procedure.

## Headless testing

The kernel is pure and fully unit-tested. `wiring/` is not reachable headlessly (it imports the Obsidian runtime, which is types-only in node), so the accept perimeter is asserted by SOURCE SCAN — module-scope, not exported, `addEventListener`-wired, `isRealGesture`-gated — and every scan is proven against a planted violation before it is trusted. The definitive proof is the deploy-time live reachability walk; the source tripwire is what catches a regression before it.

The cross-plugin round trip cannot be reached at all: two Obsidian plugin instances, one registering on the other's `api` object, needs a renderer. `docs/s3c-migration-plan.md` §8 is the live checklist for it.
