# Vault Vocabulary (plugin id `vaultmcp-vocab`) — architecture & working notes for Claude Code

The vault's controlled vocabulary as its own Obsidian plugin: enumerate the configured vocabulary sources, resolve a tag / property key / type name / glossary term, report a note's own vocabulary, validate one note's frontmatter against the registries — published to the Governor host through `vault-mcp-api`. Report-only; nothing here writes to a note. Extracted from the host at the suite split's S7 (`docs/suite-split-design.md` §6, "Vocabulary provider | public optional | satellite"), following `packages/quickadd-choices-compile` (the pilot), `packages/skills` (S4), `packages/triage` (S5) and `packages/crosssession` (S6). Package layout, build/test commands, and the extraction's five consequences are in `README.md`.

## Locked decisions (don't relitigate without reason)

- **THE KERNEL LIVES IN `@vault-mcp/core`, AND THERE IS NO SECOND COPY HERE — this is the headline decision.** `packages/core/src/vocab/` holds `provider.ts`, `blueprint.ts`, `glossary.ts`, `scope-tags.ts`, `findings.ts` and `registry.ts`, and this package imports every one of them from `@vault-mcp/core`. It is NOT the skills/triage/crosssession shape, where the kernel moved into the satellite, and the difference is a fact about the code rather than a preference: the vocabulary kernel has TWO consumers and always did — these four tools, and the HOST's conformance rail (`conformance/packs/vocab.ts` wraps `noteVocabFindings`, `conformance/cli.ts` builds a `VocabRegistry` per run, and `conformance/snapshot.ts` / `rule-pack.ts` are typed over `VocabNote`). That dependency is on the KERNEL, not on the setting — the rail builds its registry from `DEFAULT_VOCABULARIES`, see the host-observation bullet below — which is exactly why the kernel is shared and the setting is not. Moving the kernel here would have forked it, and **two copies of a rule core is how one vault gets two vocabularies** — a drift with no loud failure, only a slowly diverging answer to "is this tag registered". Publishing into core is the `isVisible` (S4) and `executeQuickAddChoice` (S5) precedent, and conformance is itself a planned satellite (§6), so core is where both consumers end up meeting anyway. **If you find yourself wanting a `src/kernel/` in this package, stop.** The same rule makes `visiblePaths` here a three-line local wrapper over core's published `isVisible` rather than a second copy of the predicate.

- **THE ALLOWLIST POSTURE IS PER TOOL, AND FOR ONE TOOL PER CALL — do not round it off to a sentence.** Every prior satellite could say "the host blocks the whole surface under an allowlist". That is FALSE here and rounding it off would misdescribe the perimeter in both directions. The host's F3 gate (`external-tools.ts:209-229`) is `settings.allowlist.length > 0 && collectPaths(args ?? {}).length === 0`, evaluated at CALL TIME on the ACTUAL ARGUMENTS. So: `vocabularies` (no arguments) and `list_vocabulary` (`kind` / `scope` / `vocabulary`, none a path key) are blocked outright; `validate_terms` REQUIRES `path`, a recognized path key, so it stays available and the host scopes it; and `resolve_term`'s `path` is OPTIONAL, so **the same tool is blocked when called with `{token}` and scoped when called with `{path}`**. Pinned by the `publication` tests, including the per-call asymmetry through the host shim's `carriesPathKey`. `scope` was deliberately NOT renamed into a path key: it filters the DECLARING PATHS of entries already in the listing rather than naming what the call reads, so path-keying it would hand the guard a prefix while the actual reads stayed unscoped — the illusion of a check, the same reasoning that kept `channel` off the list at S6.

- **THE SETTING IS A TOP-LEVEL ARRAY, NOT `modules.vocab.config` — and its fate is the ordinary one.** Vocab never had a `modules.vocab.config`: `VOCAB_MANIFEST` carries no `config:` block, because the setting is a LIST of structured instances the scalar manifest-field renderer cannot express, so it lived at the host's top level (`settings.vocabularies`) with a bespoke per-instance form beside it. That is the only way this extraction's settings story differs from skills'/triage's/crosssession's — the SHAPE of the source. Its fate is identical: after S7 **nothing in the host reads it**, `getVocabularies` is gone from the server context, and the host's bespoke form and its pure helpers were REMOVED (they became unreachable when the vocab module left `builtinModules`). This package now holds the only copy of both the setting and the form — a MOVE, not a fork. The field is still declared and defaulted in the host's `main.ts` deliberately, as the ADOPTION SOURCE, so deleting it cannot destroy a user's configuration before this plugin has read it; the host's `vocabularies` doc comment is the canonical statement of that, and this package's wording defers to it rather than restating it differently.

  **An earlier draft of this file asserted the opposite** — "two live, independently-edited copies", on the grounds that the host's conformance rail reads the setting — and it was WRONG. Recorded so nobody re-derives it: `runConformance` does take an `opts.vocabularies`, but its three call sites (`mcp/obsidian-drift-source.ts`, `mcp/obsidian-debt-source.ts`, `conformance/cli.ts`'s CLI entry) all pass `DEFAULT_VOCABULARIES` unconditionally. Taking an option is not reading a setting; check the call sites.

- **HOST OBSERVATION, not a consequence of this split: conformance checks vocabulary against the SHIPPED DEFAULTS.** The rail depends on the vocabulary kernel — which is precisely why the kernel went to core — but it builds its registry from `DEFAULT_VOCABULARIES` and has never honoured the user's configured instances. So in a vault with a customised vocabulary, conformance findings and this plugin's tools can genuinely disagree about what is registered. That was true before the extraction and is unchanged by it; the split only makes it easy to see, because the configured list now visibly lives somewhere else. Flagged in the settings tab as Governor's caveat rather than this plugin's. Whether conformance SHOULD honour the configured list is a live host question and a separate decision — do not "fix" it from this side, and do not paper over it either.

- **Adoption is ALL-OR-NOTHING because the setting is a LIST.** The three rules are unchanged (never writes the host's settings; runs once; the satellite's own values win), but "own values win" for an array means adoption happens only when this plugin has NO rows. A row-by-row merge would need an identity to merge ON, and the only candidate (`id`) is exactly what a user renames — so a merge would silently resurrect a row they deleted here. Structural garbage in the incoming array is dropped through `coerceVocabInstances`; an unknown provider NAME is KEPT, because the registry skips-and-reports it and the settings form flags it, and dropping it would hide a misconfiguration the user needs to see. `hostSettings === undefined` means HOST NOT READY, never "host with empty settings" — the host declares `settings` without an initializer and assigns it mid-onload, so the check in `main.ts` is `!== undefined` and never a truthiness test; treating it as an empty host burns the one-shot latch on nothing.

- **The dormant `visible` seam costs something here, unlike in triage and crosssession, and saying otherwise is the failure mode to avoid.** Nothing supplies `ctx.visible` / `ctx.getSettings` in the shipped configuration — a satellite cannot reach the host's guard settings. For the two tools the host blocks outright that is unreachable. For the two it lets through, the providers are built from the WHOLE vault listing while the host scopes only the `path` ARGUMENT, so under an allowlist `validate_terms` and `resolve_term`-with-`path` can disclose, for tokens the caller's own VISIBLE note already carries: whether a hidden registry declares them, whether they are retired, their `definition` gloss (frontmatter text from a possibly-hidden registry note), and — through the `ambiguous` finding's `VocabAmbiguousError.candidates` detail — the PATHS of registry notes claiming a duplicated token. It is bounded (you can only ask about tokens you can already read) but it is a genuine loosening relative to the folded module, which filtered the listing. Do NOT delete the seam to "simplify": its tests supply it so it cannot rot, and an apiVersion-2 `vault-mcp-api` that carries the caller's scope to a publisher makes it live again with no code change. One test (`UNSUPPLIED — the shipped configuration…`) pins what its absence actually does, so nobody rediscovers this as a surprise.

- **Path-shaped arguments this package validates BY HAND refuse a backslash outright.** `resolve_term`'s optional `path` and `validate_terms`' required `path` are checked here with `isVisible`; `list_vocabulary`'s `scope` is passed straight to `provider.list(kind, scope)`. Every check downstream of those splits on `/` alone — the host guard's `collectPaths` + `normalizePosix`, `isVisible`'s prefix match, the providers' own `underRoot` — so `Notes/x\..\..\Secrets.md` reads as ONE opaque segment here and as a traversal to whatever normalizes it later. Obsidian paths never legitimately contain a backslash; refusing closes the class rather than the instance. Codes: `invalid_path` (new) for the two `path` arguments, `invalid_scope` for `scope` — matching the vocabulary `resolveScope` and the host's `tools-locks.ts` already use for a bad scope. **`token` and `vocabulary` are deliberately NOT refused**: neither is ever split as a path, prefix-matched, or handed to `isVisible`, so a backslash in one is an ordinary character that fails to resolve — refusing it would reject a legitimate (if odd) token for a threat that does not exist on that argument. Each is pinned by test, including the non-refusal.

- **`scope` is NOT routed through core's `resolveScope`, and that is a decision.** `resolveScope` is where this repo's one copy of scope validation lives, and reusing it would normally be right. It is wrong here: `resolveScope` answers "may this session READ under this prefix" — it normalizes the prefix, refuses `""`, and applies an allowlist branch this satellite cannot evaluate. `list_vocabulary`'s `scope` is a filter over the DECLARING PATHS of entries already in the listing, where `""` is a first-class value meaning "everything" (the providers' `list(kind, "")` returns all). Routing it there would change shipped behaviour well beyond the class the backslash refusal closes. The one-line backslash check is not a fork of a predicate — `resolveScope` and triage's `plan.ts` each carry their own copy of the same line for the same reason.

- **Handlers return plain data and THROW on refusal**, with a lowercase-snake `code`; the host's `fail()` renders `Error [code]: message`. `ok` / `fail` / `codedError` are host-internal and are not imported here. **TWO ENVELOPES CHANGED, on purpose:** the module returned `fail(new Error("give \`token\` or \`path\`, not both — …"))` and `fail(new Error("give \`token\` … or \`path\`"))` for the two argument-shape errors, which rendered CODELESS as `Error: …` — the only refusals on this surface an agent could not branch on. As a satellite they are thrown refusals carrying `invalid_argument`. `vocab_ambiguous` and `out_of_allowlist` keep their exact codes and messages, byte for byte, and are pinned that way.

- **Re-apply every schema bound in the handler.** The SDK converts zod to JSON Schema and the host converts it back through a small subset (`src/mcp/json-schema-to-zod.ts`): `type`, `description`, STRING `enum` and the object's `required` list all survive; `default`, `min`, `max` and `pattern` do NOT. So every `.min(1)` runs again in `requireText`. `kind`'s enum and `list_vocabulary`'s requirement of it DO survive — and are re-checked anyway (`requireKind`), because both handlers branch on the value and the SDK also accepts a hand-written JSON Schema whose bare `{}` property degrades to `z.unknown()`. This is the `vaultmcp_skills_release` semver lesson: if you add a constrained argument, constrain it twice.

- **The published names dropped the `obsidian_` prefix, and that half of the rename was CHOSEN, not forced.** `vaultmcp-vocab` sanitizing to `vaultmcp_vocab` is the id's consequence, like every prior satellite. Stripping `obsidian_` from the bare names is separate: the host's F1 check rejects a PUBLISHED name starting with `obsidian_`, and `vaultmcp_vocab_obsidian_vocabularies` does not, so it would have registered — it would just have named the module twice and the namespace not at all, because `obsidian_` was the HOST's built-in namespace. The rename table is in `README.md`; it BREAKS any agent session or saved prompt calling the old names, and reversing the namespace is a one-line change (the plugin id, plus the strings in `tests/host-shim.mjs` and the settings tab).

- **An EMPTY configured list means the shipped defaults.** In the host, `getVocabularies` was always supplied and an empty array meant "no vocabulary at all". Here `rows()` falls back to `DEFAULT_VOCABULARIES` when the list is empty, because a fresh satellite install starts empty with no host to adopt from and doing nothing out of the box is not what installing a vocabulary plugin asks for — and because the host's now-removed form already told users this was the behaviour, untruthfully. Configuring "no vocabulary at all" is what disabling the plugin is for. Pinned by test.

- **Config is read PER CALL, never captured**, and `main.ts` re-publishes on every settings write anyway. `ctx.getVocabularies` is a thunk, so handlers always see the live rows; but the host SNAPSHOTS a published spec's schema and description when it registers it, and the descriptions are what an agent reads to decide whether to call a tool at all. Today none of the four descriptions interpolates a configured value — the rule still applies, because `vocabularies` is precisely the tool that ENUMERATES the configured rows and its description is one edit away from wanting them, and because re-publishing costs nothing. Do not "simplify" `republish()` back into a single `this.register(publishTools(...))` in onload.

## Build / test

- `npm run build` — esbuild, emits `main.js`. No assets, no defines: like the triage and crosssession satellites and unlike skills, there is nothing to embed.
- `npm test` — `pretest` builds `@vault-mcp/core`, then `tsc --noEmit && node --import tsx --test`. **The `pretest` is load-bearing twice over here:** the tests reach `isVisible` AND the entire vocabulary kernel through `packages/core/dist` — the COMPILED output. Without the rebuild you test the previous build's bytes.
- Install for testing: copy `main.js` + `manifest.json` into `<vault>/.obsidian/plugins/vaultmcp-vocab/` and reload the plugin. During development add an empty `.hotreload` file in that directory so the hot-reload plugin picks up rebuilds — it belongs to the vault install, not to this repo.

## Headless testing

Everything except `src/obsidian-source.ts` and `src/settings-tab.ts` is unit-tested without Obsidian: the tool handlers run over a fake `VocabSource` (a plain object of `{path: {frontmatter?, body?}}`), the adoption and the settings-list helpers over plain records. `tests/host-shim.mjs` reproduces the three things the host does to a published tool — the `<sanitized id>_<bare name>` naming, the `ok()`/`fail()` envelopes including the coded rendering, and the annotations it derives from an UNTRUSTED `readOnly` claim — so the tests assert the envelopes an agent actually sees rather than raw return values. It also carries the host's `PATH_KEYS` **as data**, plus a `carriesPathKey(args)` predicate, which is what lets this package pin the per-call asymmetry.

`HOST_PATH_KEYS` is a REVIEW AID, not a live tripwire: it is a snapshot copy, so a host edit to the real list does not fail a test here. The test that actually fires when the host changes the list is the host's own `tests/guard.test.mjs` pin over the live `collectPaths`. What this package legitimately owns is the other half — which of ITS OWN argument names appear in that list — and that is what the assertions read.

The shim deliberately does NOT reproduce the F3 pathless-tool block, the path allowlist, the write queue, the journal, read-only mode, or the record-immutability guard. Those are host code with host tests, and a second copy could drift into asserting a posture the host does not enforce.

`src/obsidian-source.ts` is NOT reached headlessly. Two things in it are easy to get wrong and are worth checking live: it enumerates `vault.getFiles()` and **not** `getMarkdownFiles()`, because the blueprint provider's TYPE entries are `.fileclass` files; and it reads bodies through `cachedRead` only for the files the tool layer's `buildListing` decided need one (a `.fileclass` under a blueprint root, markdown under a glossary `termsRoot`, and the folder notes plus the root scope note a scope-tags vocabulary reads its `## Tags` tables from), never the whole vault.
