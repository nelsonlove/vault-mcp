# Vault Skills (plugin id `vaultmcp-skills`) — architecture & working notes for Claude Code

The skills compiler as its own Obsidian plugin: it compiles the vault's skill / agent / policy / command notes into a Claude Code plugin on disk, and publishes six MCP tools to the Governor host through `vault-mcp-api`. Extracted from the host at the suite split's S4 (`docs/suite-split-design.md` §6, "Skills compiler | private operator | satellite"), following the `packages/quickadd-choices-compile` pilot. Package layout, build/test commands, and the extraction's two consequences are in `README.md`; the user-facing model is `docs/skills.md` at the repo root.

## Locked decisions (don't relitigate without reason)

- **The six tool names are historical and do NOT change.** `vaultmcp_skills_validate`, `_tree`, `_preview`, `_export`, `_release`, `_mark`. Each spec in `src/tools.ts` carries only the BARE half (`validate`, …); the host publishes an external tool as `<sanitized publisher id>_<bare name>`, and `vaultmcp-skills` sanitizes to `vaultmcp_skills`, so the shipped spellings reproduce exactly. This is the host's own precedent for `governance_revisions` / `governance_submit_revision`: renaming shipped tool names breaks agent sessions for zero semantic gain. **A consequence to keep in mind: the plugin id and the tool namespace are the same string.** Renaming the plugin id renames every tool.

- **The compile reads the WHOLE of the configured roots, and nothing scopes what it compiles below that.** Parent edges span the tree, so a partial compile produces a broken plugin; every filter that answers a caller (the allowlist, the preview visibility filter) acts on what is RETURNED, never on what is compiled. Since #404 (ruled 2026-09-26) the roots themselves are a SETTING: `includeRoots` / `excludeRoots` name the folders the compile reads, and the plugin ships them EMPTY, so nothing compiles until the operator names their folders. A parent outside the roots is a broken edge and is reported as an error naming the child (`unresolved parent`), never silently re-hung; the roots narrow the vault the compile sees, they do not partially compile it. The same ruling made the vault's spelling of each kind a setting: `typeMap` (`<vault type> = skill|agent|policy|command`), shipped EMPTY; the KERNEL keeps an identity map (`IDENTITY_TYPE_MAP`) for its direct callers, so the plugin assumes no class name and the compiler API is unchanged. `mark` writes the MAPPED spelling and refuses a kind the map does not name. **An export that compiled zero notes REFUSES** before touching disk: the stale-file cleanup deletes whatever the previous manifest listed and this run did not produce, so a first export under the empty defaults would otherwise wipe the previous export (found by the #405 review). The `~/.claude/agents` symlink loads the rank definitions natively today, so the roots are also how the fleet keeps that folder out of the compile until the switch; the switch test in `tests/skills-settings-404.test.mjs` is the one the fleet runs before retiring the symlink.

- **THE ACCEPTANCE GATE (01.41 rule 8; ruled 2026-09-27 with 01.61 rule 11 repaired to strict exclusion): nothing unaccepted reaches a compiled agent prompt.** `collectNotes` excludes every typed note that does not carry a `verified` entry naming a `human:` actor, whatever its kind and whoever called — the kernel's direct callers included — using core's `hasHumanVerification`, kept in core beside the accept guard as the one definition of the accepted state for both readers (the guard itself refuses agent writes to `verified` and does not read this predicate). The rule is over the prompt's TEXT, so EMBEDS are gated too: an accepted note's `![[X]]` of an unaccepted note is not inlined, a marker stands in place of each embed, and the note's path is recorded once (`excluded.transclusions`, distinct notes) and kept as an export source so accepting X later re-runs the export. The shipped embed lookup carries the cache's frontmatter (`EmbedSource.frontmatter`) so both gates read one parse of a note; a lookup without it falls back to core's guard parser over the raw text, failing closed. Excluded notes are counted per kind, named, and reported on all three surfaces (`Analysis.excluded`, `PreviewResult.excluded`, `ExportSummary.excluded`, plus one warning line); an unratified policy is injected nowhere. There is no switch to turn the gate off. **The compiled artifact records each source's acceptance** (01.61 rule 11, rewritten on Nelson's "b", 2026-09-29): every compiled file's generated header carries an `acceptance:` block with one line per source — its own note, each injected policy, each transcluded note — naming the human `verified` actor and date (core's `humanVerificationOf`, which describes exactly the notes `hasHumanVerification` accepts), and a refused embed as NOT accepted. The records are filled at collect time by the same gate, so a line cannot claim acceptance the gate did not check; a bare `transformAll` call with no map writes no block. The consequence for the switch (the six rank definitions at 03.18) is the rule's: they compile only after Nelson verifies them.

- **The allowlist boundary is the HOST's, and it is stricter than the filter it replaced.** The in-tool visibility filter in `src/tools.ts`'s `preview` handler is retained in full and does nothing in the shipped configuration — nothing supplies `ctx.getSettings`, because a satellite cannot reach the host's guard settings, so it degrades through the same `!settings ||` branch it always had. What actually enforces: the host distrusts an external tool's `readOnlyHint: true` unless the publisher's RAW id is in its `trustedReadOnlyPlugins`, so all six register as MUTATING; and an external tool — trusted or not — whose arguments carry no recognized path key is BLOCKED OUTRIGHT while a path allowlist is active (the trusted exemption was closed 2026-09-05; trust answers read-only mode, never scoping). Five of the six carry no path argument ⇒ refused wholesale. `mark` carries `path` ⇒ scoped normally. **Do not delete the dormant filter** — the assembled-body reasoning inside it (an entry's own source, everything it transcludes, AND every `type: policy` note injected into an agent; plus the `"(static)"` marker, which is not a vault path) was found by an independent review of a first fix that checked only the entry's own `from`, and it becomes live again when `vault-mcp-api` can carry the caller's scope to a publisher (an apiVersion-2 item). Its tests supply `getSettings` themselves so it cannot rot.

- **`isVisible` / `GuardSettings` come from `@vault-mcp/core`, never a local copy.** They were published there at this extraction precisely so the host's `guard.ts` and this plugin ask one question. A second copy of a guard predicate is the drift this repo has paid for twice.

- **`vaultmcp_skills_mark` runs the accept-forbidden guard before any write** (`guardSkillsMark` in `src/tools.ts`): it computes the frontmatter the mark WOULD land and runs `acceptTransitionReason` from `@vault-mcp/core` — the same predicate the fs and Obsidian write primitives use. A mark can never introduce or change an `accepted` / `accepted-by` / `accepted-on` field, or set `acceptance-status` to an accepted value; carrying an existing human-granted value forward unchanged is allowed. The GUI `mark` command routes through the identical function, so the human path is not a bypass. Extraction did not weaken this: the predicate is a published core contract. Pinned by `tests/skills-module.test.mjs` — including that a refusal blocks the WRITE, not just the response.

- **Handlers return plain data and THROW on refusal.** The host wraps a return value in `ok()` and a thrown error in `fail()`, so the envelopes agents see are unchanged from the folded era. There is no `ok`/`fail` import here; those helpers are host-internal.

- **Config is read PER CALL, never captured.** `SkillsToolsCtx.config` is a thunk. The host holds a spec snapshot per connection, so a captured config would freeze the settings tab's values at plugin load.

- **Settings adoption is one-shot and never writes the host.** See `src/settings.ts`. Three rules, each pinned: it never writes the host's settings (the host's copy stays and simply stops being read); it latches (`adoptedFromHost`), so a later host edit cannot reach back in; and this plugin's own values win, adoption only filling gaps. A host that is ABSENT adopts nothing and does NOT latch, so a standalone install keeps its one chance for later.

- **The plugin works with no host installed.** The pane, commands, ribbon and export-on-save are pure Obsidian plus the compiler core; only the tools go unpublished. `main.ts` wires the human surface BEFORE it publishes so the claim and the code agree (`publishTools` is internally defensive, which makes the ordering belt rather than fix — the pilot's reasoning).

- **The compiled edge model** (`src/kernel/`, #292). The compiled output is **FLAT** (`skills/<name>/SKILL.md`, `agents/<name>.md`; `genName` derives from the note's own name, not tree position), so every emitted skill is reachable by every emitted agent through the Skill tool. Consequences, all deliberate: **(1)** `parent:` is an organizational/provenance edge and is MULTI-VALUED — the FIRST parent is PRIMARY (tree edge, breadcrumb, `level`, ownership, reachability/cycle checks), the rest are recorded ATTACHMENTS with no effect on any compiled path; every named parent is still validated; `type: policy` keeps STRICT single-parent (its parent is a lineage edge, and a second would mean a second injection site). **(2)** The agent `skills:` frontmatter is PRELOAD, not permission — emitted from an OPT-IN per-skill `preload: true`, never from attachment alone; `preloadCap` (default 5) WARNS, never refuses. **(3)** `no-skills: true` on an AGENT compiles `disallowedTools: [Skill]` — `disallowedTools` rather than a `tools` allowlist is load-bearing, because it applies BEFORE `tools` resolves and so leaves the agent's other tools alone. The full reasoning is the decision-record bullet in `packages/host/CLAUDE.md` (kept there deliberately: that file is the record of what was decided, and the extraction did not re-decide it) and the user-facing form is `docs/skills.md`.

## Build / test

- `npm run build` — esbuild, emits `main.js`. The build embeds `assets/new-skill/SKILL.md` and `conventions.md` as the `__NEW_SKILL_MD__` / `__NEW_SKILL_CONVENTIONS__` defines that `src/kernel/static-skills.ts` reads; absent assets ⇒ empty defines ⇒ `STATIC_FILES` is empty, which is exactly what happens under `tsx` in tests.
- `npm test` — `pretest` builds `@vault-mcp/core`, then `tsc --noEmit && node --import tsx --test`. **The `pretest` is load-bearing, not tidiness:** the tests import published core contracts, which resolve to `packages/core/dist` — the COMPILED output. Without the rebuild you test the previous build's bytes.
- Install for testing: copy `main.js` + `manifest.json` into `<vault>/.obsidian/plugins/vaultmcp-skills/` and reload the plugin. During development add an empty `.hotreload` file in that directory so the hot-reload plugin picks up rebuilds — it belongs to the vault install, not to this repo.

## Headless testing

Everything except `obsidianSkillsBackend` is unit-tested without Obsidian: the compiler core runs over an injected `SkillsSource`, the tool handlers over a fake `SkillsBackend`, the accept guard over plain objects, the export-on-save debounce and change-relevance predicate over plain values, and the settings adoption over plain records. `obsidianSkillsBackend` (the `app.vault` / `app.metadataCache` / `app.fileManager` adapter), the pane, and the modals are the parts that need a running Obsidian. Keep new logic on the Obsidian-free side of that line — it is why this package moved between three homes without losing coverage.
