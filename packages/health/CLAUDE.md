# Vault Health (plugin id `vaultmcp-health`) — architecture & working notes for Claude Code

The vaultmcp-health scanner as its own Obsidian plugin: a tiered read-only findings scan over the whole vault, and the same scan with findings restricted to one folder — published to the Governor host through `vault-mcp-api`. Extracted from the host at the suite split's S7 (the read tier), following `packages/quickadd-choices-compile` (the pilot), `packages/skills` (S4), `packages/triage` (S5) and `packages/crosssession` (S6). Package layout, build/test commands, and the extraction's five consequences are in `README.md`. There is no repo-root user doc for health (`docs/` has `skills.md` and `triage.md` but no `health.md`); the tool descriptions and this package's two files are the documentation.

## Locked decisions (don't relitigate without reason)

- **The published tool names CHANGED, and that was a deliberate trade — this is the one thing to know before touching anything here.**

  | shipped (module) | bare name here | published (satellite) |
  |---|---|---|
  | `obsidian_health` | `scan` | `vaultmcp_health_scan` |
  | `obsidian_lint`   | `lint` | `vaultmcp_health_lint`  |

  It breaks any agent session or saved prompt calling the old names, and that cost is real — the host's own locked decision says renaming shipped tool names breaks agent sessions for zero semantic gain. Two compositions produce the new names: the host publishes an external tool as `<sanitized publisher id>_<bare name>` (`sanitizeOwnerId`, `packages/host/src/mcp/external-tools.ts`), so **the plugin id IS the tool namespace** (`vaultmcp-health` → `vaultmcp_health`); and the BARE names shed `obsidian_`, on exactly the grounds the bases satellite used for shedding `base_` — **`obsidian_` was the HOST's built-in tool namespace, never this module's own name**, so carrying it into a satellite's namespace publishes a tool named after two owners.

  **The alternative existed and was NOT taken, and getting this wrong is easy — do not restate it as forced.** F1 tests the **PUBLISHED** name, not the bare one: `const toolName = ${owner}_${spec.name}; if (toolName.startsWith("obsidian_")) throw`. A bare `obsidian_health` under this plugin id publishes as `vaultmcp_health_obsidian_health`, which does not start with `obsidian_`, so F1 never fires and `NAME_RE` accepts the bare name — it would have registered fine, just stutteringly. What buys the rename is readability and the prefix naming the wrong owner, nothing structural. (An earlier draft of this file claimed F1 forced it; corrected 2026-09-05 after re-reading `external-tools.ts`, and the same correction landed in the vocab and bases packages so the three do not contradict each other.)

  **Reversing it is a one-line change** — `manifest.json`'s `id` for the prefix, plus the strings in `tests/host-shim.mjs` (`PLUGIN_ID`) and the settings tab's status line; the BARE names live only in `src/tools.ts` and those same two places. Nothing else in the package encodes either half. Pinned by the `publication` test.

- **`scope` is NOT a path key, and renaming it into one would be wrong — this is the decision that distinguishes this extraction from triage's.** The host's `PATH_KEYS` are `path`, `from`, `to`, `target_path`, `template_path`, `subdir`, `file_path`, `output_folder` (plus the array keys `paths`, `refs`). Triage renamed `target` → `target_path` because `target` WAS the destination the call named and the host could then scope it. Here the analogous move is wrong three times over:
  1. **It is not the path of anything the tool reads.** `scope` is a folder PREFIX and a filter over FINDINGS. `scanHealth` reads every note by design; the scope only narrows what is REPORTED. Path-keying it would hand the guard a string that does not describe the read.
  2. **It would be the illusion of a check.** `lint` accepts a folder OR a note path, and the host's `isVisible` prefix-match is fine with both — so the guard would let a scoped `lint` through while the underlying scan still read the whole vault. That is exactly the trap the cross-session extraction named when it declined to path-key `channel`.
  3. **The `to` → `to_address` precedent runs the other way.** The host renamed AWAY from a path key when the argument was not a path. The direction of that precedent is "do not path-key a non-path", not "path-key anything path-shaped".

  The consequence is that BOTH tools are blocked wholesale under an active allowlist (`scan` has no arguments at all, so it was always going to be). That is fail-closed, strictly stricter than the in-module non-filtering it replaces, and it is stated in the README and the settings tab. Pinned by test (`publication: … NEITHER argument list carries a host path key`).

- **Be exact about the allowlist posture; do not overclaim.** The host's F3 gate (`external-tools.ts`) is evaluated **at CALL TIME on the ACTUAL ARGUMENTS**, not on the declared schema: `if (settings.allowlist.length > 0 && collectPaths(args ?? {}).length === 0) return fail(...)`. So the correct statement is per tool: `vaultmcp_health_scan` takes no arguments ⇒ blocked outright under an allowlist; `vaultmcp_health_lint` takes `scope`, which is not a path key ⇒ also blocked outright. Both declare `readOnly: true`, which the host DISTRUSTS unless `vaultmcp-health` is listed in the user's **`trustedReadOnlyPlugins`** setting; untrusted ⇒ both register as MUTATING ⇒ read-only mode blocks them and each call takes a write-queue slot and a journal record. **Trust answers read-only mode, never scoping** (closed 2026-09-05 by the skills satellite's review) — adding the plugin to `trustedReadOnlyPlugins` does not make either tool available under an allowlist.

- **Issue #381 is RESOLVED for these two tools, and the framing matters more than the verdict.** #381 named three whole-vault scanners with no allowlist filtering — `obsidian_health`, `provenance_reconcile`, `obsidian_conformance_debt` — and asked for either an enumerated exception or a decision to filter. Do not write "we made health filter": it does not. The whole-vault read is UNCHANGED in the code, `scanHealth` still reads every note, and the reason is still correct (a partial report misreports orphans, because an attachment referenced from outside the allowlist reads as orphaned, and loses duplicate-group members). What changed is WHERE the boundary is enforced: as untrusted external tools with no recognized path-key argument, both are blocked wholesale by F3 under an allowlist — stricter than the documented-exception outcome #381 was weighing. With no allowlist configured nothing changes, because there was nothing to filter against. **The issue's three-tool list shrinks to two** (`provenance_reconcile`, `obsidian_conformance_debt`, both still in the host, both still owed the decision). [Update 2026-10-14: `obsidian_conformance_debt` has left the host too, as the `vaultmcp-conformance` satellite's `vaultmcp_conformance_debt`, refused outright under an allowlist on the same terms; no tool on #381's list remains in the host. See `packages/conformance/CLAUDE.md`.] This claim is about `vaultmcp_health_*` only — the sibling vocab and bases extractions are not on #381's list and nothing here speaks for them.

- **`resolveScope` comes from `@vault-mcp/core`, and nothing here re-implements it.** Same reasoning as `isVisible` at S4 and `executeQuickAddChoice` at S5: a second copy of a guard predicate is the drift this repo has paid for three times, and a copy that normalizes differently is a bypass nobody notices until it is a leak. It was PUBLISHED at S7 (`packages/core/src/scope.ts`) rather than copied, is behaviour-preserving (the host's version's whole dependency reduced to `isVisible`), and gained ONE new refusal — **a scope containing a backslash refuses `invalid_scope`**, because every downstream check splits on `/` alone. That made BOTH callers stricter in the same motion (the host's `obsidian_check_links` and this `lint`), which is the point of there being one copy. Core's own tests pin the function; **this package pins that its tool SURFACES the refusal** as `Error [invalid_scope]` through the host envelope. If you ever need a scope check somewhere else in this package, call the same function.

- **KEEP the in-handler scope guard.** It is redundant *under* an allowlist — F3 has already refused the call before the handler runs — but load-bearing WITHOUT one, which is the configuration the operator actually has. It still validates malformed scopes: absolute, `..`-escaping, whitespace-padded, backslashed, and ones normalizing to nothing. It is also the surviving record of a real bug: until 2026-08-29 `obsidian_lint` did not check `scope` at all (a bare string is not in `PATH_KEYS`, so `guardCall` never saw it), and a session allowlisted to `Projects/` could lint `Archive/Secrets` and get back dangling-link text, orphan-attachment paths, empty-note paths and duplicate-group paths for a folder it could not otherwise see, with `ctx.getSettings` sitting on the context declared and never called. Do not "simplify" the guard away on the grounds that the host now blocks the tool.

- **Refusals are TYPED, never a zeroed report.** A zeroed report for a hidden folder and a zeroed report for a genuinely clean one are indistinguishable, so `out_of_allowlist` and `invalid_scope` refuse rather than returning empty findings. Same precedent as the host's `scopeRefusal` and `obsidian_check_links`.

- **`ctx.getSettings` is a live seam for the SCOPE and a deliberate non-application to the SCAN.** Two different things that are easy to conflate. It is passed to `resolveScope` to validate the `scope` argument. It is NOT applied to `scanHealth`, which reads the whole vault on purpose. In the shipped configuration `main.ts` supplies nothing, so the allowlist half of `resolveScope` is dormant and only the malformed-scope half runs; the tests supply it so the behaviour cannot rot, and an apiVersion-2 `vault-mcp-api` that can carry the caller's scope to a publisher makes it live again with no code change. Do not delete it, and do not wire it into the scan.

- **Config is read PER CALL, never captured — this was a REAL BUG, fixed in the move.** `registerHealthTools` computed `const cfg = healthConfigOf(ctx.config)` ONCE at registration and both handlers closed over it. As a module that was per-connection, so a settings edit landed on the next agent connect. As a satellite there is **no per-connection rebuild at all**, so the captured config would have frozen the threshold at plugin load forever. `HealthToolsCtx.config` is therefore a thunk (`cfgNow()`), and the build-time snapshot (`cfgAtBuild`) exists ONLY for the tool DESCRIPTIONS, which render the configured threshold and which the host snapshots when it registers a spec. That is why `main.ts` **disposes and re-publishes on every settings write**. Do not "simplify" `republish()` back into a single `this.register(publishTools(...))` in onload: the threshold an agent reads in the tool list would misreport until an Obsidian reload. Both halves are pinned by test (`config is read PER CALL`, `the tool DESCRIPTIONS snapshot the threshold at build time`).

- **Settings adoption is a ONE-SHOT LATCH, and `hostSettings === undefined` means HOST NOT READY.** The three rules are the skills/triage/crosssession ones: never write the host's settings, run once, this plugin's own values win. The subtlety worth restating: the host declares `settings` without an initializer and assigns it mid-`onload`, so an instance visible in `app.plugins.plugins` before that assignment must NOT burn the latch. The check in `main.ts` is `host.settings !== undefined`, **never a truthiness test** — treating a not-ready host as "host with empty settings" burns the one chance on nothing and the user's config never adopts (found by the skills extraction's review). Failure paths hold the latch OPEN: an absent host, a not-ready host, and a `saveData` that throws all leave `adoptedFromHost` false so the next load retries.

- **There is exactly ONE adoption, and the absence of a second is a checked fact.** Cross-session had to migrate live operator state (`crosssession-receipts.json`). Health has none: the module kept nothing on disk — no baseline, no cursor, no receipts — because every call recomputes the whole scan from the live metadata cache and the notes themselves. `modules.health.config` (one field, `emptyChars`) is the entire migration surface. Pinned by a test over `DEFAULT_PLUGIN_SETTINGS`'s key set so a future reader does not have to wonder whether a second latch was forgotten.

- **Re-apply every schema bound in the handler.** The SDK converts zod to JSON Schema and the host converts it back through a small subset (`packages/host/src/mcp/json-schema-to-zod.ts`): `type`, `description` and string `enum` survive; `default`, `min`, `max`, `pattern` do NOT. `scope`'s `.min(1)` therefore runs again in `requireText`. This is the `vaultmcp_skills_release` semver bug, avoided rather than repeated — if you add a constrained argument, constrain it twice.

- **Handlers return plain data and THROW on refusal**, with a lowercase-snake `code` on the error; the host's `fail()` renders `Error [code]: message`. There is no `ok`/`fail`/`codedError` import here — those helpers are host-internal. `refuse()` is a function DECLARATION, not a const arrow, because TypeScript only narrows control flow through a `never`-returning call when the callee is a function declaration. No envelope changed in the extraction: this surface never used `okError`. `invalid_scope` and `out_of_allowlist` are byte-compatible with the folded era — same codes, same message text, verified against the pre-move `resolveScope` in `packages/host/src/mcp/tools-links.ts` and `guardCall`'s `out_of_allowlist` string in `packages/host/src/guard.ts`. Two things are ADDITIONS, not replacements: `invalid_argument` (the module had no re-applied schema bound to refuse with) and the backslash instance of `invalid_scope`.

- **`lint` filters and echoes the NORMALIZED prefix, not the raw argument.** The module guarded the normalized form and then filtered on the raw string, so `Projects/./Sub` could pass the guard and match nothing. One string now does both. Pinned by a test over `Projects/`, `Projects/./` and `Projects//`.

- **THIS PLUGIN NEVER WRITES.** No mutating registrar, no write guard, no accept/approve verb, and the Obsidian adapter's only vault calls are `adapter.read` and `adapter.stat`. That is the design, inherited from the standalone scanner: the scan emits findings and the fixing is a separate skill. If you are about to add a write here, you are building the wrong thing in the wrong package.

- **The scan's caveats travel with the findings and must not be quietly dropped.** A unique-basename match is NOT proof a link should be repointed (a `[[core.el]]`-style reference in a vendored or template tree can coincidentally match an unrelated note), and orphan attachments include files referenced ONLY via frontmatter or CSS, which are not in `resolvedLinks`. Both are in the tool descriptions and in `kernel/scan.ts`'s header, ported from the standalone's README.

## Build / test

- `npm run build` — esbuild, emits `main.js`. No assets, no defines: like the triage and cross-session satellites and unlike skills, there is nothing to embed.
- `npm test` — `pretest` builds `@vault-mcp/core`, then `tsc --noEmit && node --import tsx --test`. **The `pretest` is load-bearing, not tidiness:** the tests reach `isVisible` and (through the tools) `resolveScope` in `packages/core/dist` — the COMPILED output. Without the rebuild you test the previous build's bytes.
- Install for testing: copy `main.js` + `manifest.json` into `<vault>/.obsidian/plugins/vaultmcp-health/` and reload the plugin. During development add an empty `.hotreload` file in that directory so the hot-reload plugin picks up rebuilds — it belongs to the vault install, not to this repo.

## Headless testing

Everything except `src/obsidian-source.ts` and `src/settings-tab.ts` is unit-tested without Obsidian: the tiered classifier and the scope post-filter are pure over a fake `HealthSource`, the tool handlers run over the same fake, and the adoption runs over plain records. `tests/host-shim.mjs` reproduces the three things the host does to a published tool — the `<sanitized id>_<bare name>` naming, the `ok()`/`fail()` envelopes including the coded rendering, and the annotations it derives from an UNTRUSTED `readOnly` claim — so the tests assert the envelopes an agent actually sees rather than raw return values.

It also carries the host's `PATH_KEYS` **as DATA**, so this package can assert what its own argument names are NOT. That copy is a **REVIEW AID, never a live tripwire**: it is a snapshot and cannot fail when the host changes. The test that actually fires when the host adds a path key is the host's own `packages/host/tests/guard.test.mjs`, which drives the live `collectPaths` — do not claim otherwise in a comment or a report.

The shim deliberately does NOT reproduce the F3 pathless-tool block, the path allowlist, the write queue, the journal, read-only mode, or the record-immutability guard. Those are host code with host tests, and a second copy could drift into asserting a posture the host does not enforce. The module's suite used to test module-host conformance by constructing a real `fakeServer` + `mountModules`; that was possible only because it lived in the host's tree, and those assertions belong where the code is.

`src/obsidian-source.ts` is NOT reached headlessly — unlike the triage satellite there is no link-healing property here that demands driving the real adapter, because this plugin never moves, renames or writes anything. Its un-headless surfaces are the duck-typed `metadataCache` reads (`resolvedLinks` / `unresolvedLinks` / `getTags` / `getCache`) and the two vault-adapter calls; verify them live against a running Obsidian.
